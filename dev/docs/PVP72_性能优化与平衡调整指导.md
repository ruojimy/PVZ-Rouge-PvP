# PvP72 性能优化与平衡调整指导

> 后续方案（2026-11-04）：PvP72 出包与实机测量后的 V→类型化内核实验，见 [实验实施方案](PVP72_V路径到类型化CPP内核_实验实施方案.md)。本页保留较早的 r2 基线与平衡迁移规划，当前工程目录和72状态以新方案及最新发布清单为准。

日期：2026-11-04。适用工程：`PVZ-PvP71-Native`；后续 PvP72 延续独立 C++ 产品路线。本文是下一阶段实施指导，**没有实施优化、调整平衡数值或生成 PvP72 发布包**。

目标是让战斗热点真正使用有类型的数据和调用，同时改善手机显示性能。PvP72 的具体平衡改动待用户给出；可以先完成诊断、同规则性能对照和渲染排查，不必等待数值清单。

## 1. 交给下一位开发者：先做什么

1. 冻结 PvP71 r2 发布包、源码与输入清单，保存性能和功能基线，不覆盖旧包、旧报告、玩家数据。先阅读本文第 2、8 节，确认当前测试口径。
2. 将现有基准工具改造成支持“基线清单／候选清单”的版本，显式选择二进制、规则和输入。当前脚本锁定 build98，不能通过删除 SHA 检查来测新版本。
3. 接入正式原生诊断入口：PC 命令行、Android intent／配置文件，脚本连续执行三场景并导出真实数据。先核对实际画布尺寸与画质，再比较显示性能。
4. 重做当前版本热点剖析。先排查手机绘制、缩放的回退；同时选择一条完整战斗热点链做类型化试点，测量调用、分配、内存和总耗时。
5. PvP72 平衡清单到位后，先建立可运行的 72 规则基线，再把优化接到相同规则上比较。性能变化和规则变化分别记账。
6. 每个小改动做相关正确性检查和定点测量；阶段收尾跑全量、完整对拍、真实入口及设备验收。通过后再生成可追溯的 PC／APK 候选。

不要把工作停留在几处 V 运算符、查表或缓存的反复微调。局部改进可以保留，但需要以整条热点链减少动态操作的结果来判断进度。也不要未测量就承诺“再快 5–10 倍”或“达到手写 C++ 的 60%–90%”。

Core Ultra 9 275HX；用户关闭 4 AI 2v2 后测量；每场景／后端 1 次预热、3 次独立进程，交替顺序取中位数。固定逻辑 CPU 12，当次 Windows 核心拓扑检查将其识别为性能核。

| 场景 | 原生 C++ 秒 | Python＋原 C++ 扩展 秒 | 关闭扩展的 Python 秒 |
| --- | ---: | ---: | ---: |
| 空场，300 房间刻 | 1.227 | 0.851 | 1.140 |
| 基础对战，90 房间刻 | 0.536 | 0.478 | 0.585 |
| 僵尸群，60 房间刻 | 1.138 | 1.035 | 1.691 |
| 弹幕，60 房间刻 | 1.212 | 1.213 | 1.734 |

重负载原生相对关闭扩展的 Python 约快 1.43–1.51 倍；相对实际带扩展的 Python 大致持平或略慢。测试进程峰值工作集中位数 148.9 MiB，对照 376.9 MiB，约少 60.5%。后者是测试进程驻留量，不能替代整款游戏或整机的内存结论。

这里计时为 `battle.step` 循环，不含初始化、逐刻 JSON 输出、最终窗口显示、网络或 AI 策略；步进里仍可能生成绘制记录等数据，不能称为纯数学内核。旧的“约 1.65 倍”出自 11-01 的另一组代码、场景与取最小值的方法，不能和本表直接相除。

本轮限制必须随数据保留：

- 原生另做大核 4–7 绑定，实际核验已生效，FPS 变化不足 2%。不能把“绑大核”当作已证实的主要解法；它也不等于正式 APK 已接好 ADPF。
- 原生通过独立测试入口，加载与 r2 逐字节相同的五个 ARM64 游戏／SDL 库及正式资源；只增加驱动和真实 `getrusage` 绑定。**正式 APK 尚未接入这套诊断入口及该系统绑定。**
- 三场景使用真实 Application、模拟、绘制和正常回放记录，但不含 4 AI 决策、真人网络或长局热稳态。

手机已经交回用户，本指导不代表重新占用手机。下一轮设备测量安排在可用时进行，先完成电脑端与源码工作。

## 3. V 的现状与真正要改的边界

当前是没有 Python 解释器依赖的 C++ 程序，但战斗逻辑广泛使用 Python 风格动态值。是否“脱离 V”应检查实际热点执行路径，而非只看文件后缀。

已经完成的部分不要重复计为新成果：

- [value.h](../src/core/value.h) 的 `NUM` 已把 `double` 直接存入 union；不是每个数字都在堆上装箱。数字仍带类型标签，算术和接口仍可能走 V 语义。
- [obj.h](../src/core/obj.h) 的已知单位字段已经是固定成员槽，但槽的类型仍是 `V`，不等于 `double hp`、`bool frozen` 这样的原生字段。部分冷数据仍走附加字典。
- 字符串已有 `Sym`，部分槽访问、全局名和算术已有快速路径。引用对象使用非原子侵入式计数；不能笼统说全是 `shared_ptr` 原子计数。
- 历史剖析可参考[类型化改造第一步](类型化改造_第一步.md)，但 11-01 的占比不是今天的证明，需在当前候选重新采样。

### 3.1 目标：类型化一条完整链

优先评估下列链条，依据新的独占耗时、调用次数和分配量选择第一条试点：

```text
Battle::step
  → 原版植物／僵尸／实体区段、位移
  → bonus_scan、周期目标更新
  → targets.context、gate 链
  → 候选查询／洪水寻路
  → 命中、伤害、状态、生成与删除
```

原生战斗状态作为权威存储：单位字段、地图格子、目标上下文和规则参数有明确 C++ 类型；稳定的单位 ID／句柄连接系统；普通生产路径使用有类型的函数签名和直接调用。先采用便于保持语义的结构，再根据测量选择 AoS／SoA，避免先重写整个引擎布局。

V 保留在确有需要的兼容、工具、编辑器、序列化等边界。边界可以是视图、受控访问器或显式转换；应写出所有权和同步时机，避免每刻把全体单位 V→结构体→V 完整复制。高频回调必须读到同刻最新状态，不能为了省转换把同步延后到一刻结束。

第一条链交付时应给出：链上哪些函数、字段和临时对象已类型化；每 tick 动态调用、Args／小列表／字典分配、V 边界转换次数的前后变化；链耗时及完整场景耗时。整链完成后继续下一条，而不是仅用一个函数的局部倍数宣称内核整体提速。

### 3.2 保持语义的具体要求

| 风险 | 实施要求 |
| --- | --- |
| 字段缺失、`None`、零／False | 明确区分存在位与值；删除字段应恢复缺失状态 |
| 位置列表及其他共享引用 | 先梳理别名、原地修改与对象身份；不能无条件改成互不关联的值副本 |
| HeroProxy 写入拦截 | 所有影响英雄的伤害、吞咬、灰烬、冰冻等写入进入有类型的统一入口；不能因直接写字段再次绕过拦截 |
| 单位更新／候选／死亡顺序 | 保留既有顺序、同刻可见性、平局选择和延迟删除语义；不直接采用会换位的删除策略 |
| 数值与随机数 | 保留同规则执行／浮点运算顺序、舍入、随机调用次数和顺序；不顺手改为 float、fast-math 或并行归约 |
| gate 与函数替换 | 把生产链编成明确处理器；确需替换的槽提供真实覆盖路径与缓存失效，不让静态调用忽略已支持的替换行为 |
| 目标上下文 | 正常、嵌套和异常退出都恢复正确英雄／玩家状态；死亡或回调之后不能留下旧上下文 |
| 洪水／目标缓存 | 键覆盖地图、障碍、阵营、目标、规则版本及相关状态；按真实依赖失效，并保留遍历顺序 |
| 计数与索引 | 整型字段先确认范围／溢出语义；不要把单次采样只出现整数当作永久类型证明 |
| 后台任务 | 不把非线程安全 V 引用计数直接暴露给可变共享线程；延续快照冻结、所有权和取消后在途计费契约 |

固定运行路径允许静态化，但不能为通过测试保留一个从未被产品调用的“假兼容层”。反过来，CPython 内省专属断言继续按明确归属处理，不要求独立 C++ 产品重建整套 Python 解释器。

生成文件的改动应落在翻译器、手写覆盖层或有记录的生成规则。不要只改 `gen/` 再让下次生成覆盖，也不要在优化中无差别重新生成全工程、混入无关行为变化。

## 4. 手机绘制与缩放：先验证这些假设

检查入口包括 [surface.cpp](../src/pg/surface.cpp)、[draw_replay.cpp](../src/ui/hand/draw_replay.cpp)、[pixel_graphics.cpp](../src/ui/hand/pixel_graphics.cpp) 和 [graphics.cpp](../src/sim/pvp/hand/graphics.cpp)。以下是排查方向，**不是已经确认的瓶颈结论**。

1. **缩放的分配和整面拷贝。** 当前最近邻已经调用 `SDL_SoftStretch`，不是“换成 SDL 就能解决”。`transform.scale/smoothscale` 先生成结果，再由 `into_dest` 拷入目标面；有机会消除临时面或重复拷贝。先记录调用次数、尺寸、像素格式、每帧分配字节与搬运字节，再决定直接写目标或复用缓冲。
2. **像素格式与混合。** 统计格式转换、alpha／色键处理、锁面、每像素访问和逐对象 blit；对齐旧版使用的格式与快速路径。相同函数名不代表走了相同实现。
3. **重复绘制和重复处理。** 识别图像缩放、旋转、着色、文字、血条、防具和回放指令重建；可缓存不随帧改变的结果。缓存必须包含资源代次、尺寸、角度、颜色／alpha、画质等依赖，且有内存上限和释放策略。
4. **显示路径。** 分别测战场绘制、缩放、UI 合成、上传／present／等待，区分 CPU 工作与显示阻塞。不能把减少模拟推进、跳过正常回放或少画实际可见物体当作同等体验的收益。

涉及缩放或 blit 的修改，需要覆盖目标面复用、源目标别名、裁剪、舍入、色键、透明边缘和图层顺序。保留已有逐像素检查；新增检查针对真实改动风险。若要改用纹理／GPU 渲染，可先做独立原型并测端到端收益，保留原画面契约和回退路径，不在首轮顺带重构整套 SDL 后端。

30 FPS 对应整个显示帧约 33.3 ms，模拟、绘制、UI 和显示等待都要分配预算；不是给绘制独占 33.3 ms。第一阶段目标是消除相对旧版的回退，再依据设备能力确定不同负载的体验目标。目标需要测量兑现，不承诺所有场景都达到 30／60 FPS。

## 5. PvP72 平衡改动与优化怎样并行

### 5.1 两个维度，分别比较

| 标记 | 引擎实现 | 游戏规则 | 用途 |
| --- | --- | --- | --- |
| A | 冻结的 r2 实现 | PvP71 | 已发布基线 |
| B | 优化后的实现 | 同一套 PvP71 | B 对 A 测纯实现收益，并对拍 |
| C | 加入 72 平衡改动、尚未做本轮优化的实现 | PvP72 | 新规则基线 |
| D | 优化后的实现 | 与 C 完全相同的 PvP72 | D 对 C 测 72 的实现收益，并对拍 |

不必长期维护四套生产代码，可以用提交／快照、独立构建目录和规则配置复现。没有 Git 时先保存有 SHA 清单的源码快照，不能用一个随时被覆盖的 build 目录充当四个版本。

若新机制无法在旧引擎加载，就把“第一份可正确运行的新规则实现”冻结为 C；不能伪造旧引擎支持新规则。C 对 A 的速度差混合了规则、单位存活时间、弹幕数量等变化，不能全部归功于优化。最终面向玩家的 D 对 A 体验对照可以做，但必须说明规则也变了。

### 5.2 平衡修改记录模板

收到具体数值后逐项填写，不在当前阶段自行发明数值：

| 字段 | 应记录的内容 |
| --- | --- |
| 对象 | 稳定卡牌／单位／技能 ID，显示名，适用模式 |
| 改动 | 参数名、旧值、新值、单位；时间是秒、房间刻还是 native tick |
| 机制 | 冷却、触发时机、目标选择、叠加／上限、派生单位、死亡／召唤规则 |
| 关联 | 卡牌目录、商店／选卡、图鉴、UI、AI 估值／行动合法性、PvE／2v2／观战／回放 |
| 依据 | 用户决定与预期行为，哪些旧断言有意改变，哪些必须保持 |
| 负载 | 是否增加单位、弹道、目标查询、寻路、粒子或对局时长 |
| 验证 | 对应场景、独立期望、版本标记、测试结果和剩余问题 |

优先把规则参数放在有类型的规则表中，作为战斗、目录和 UI 的共同来源；新机制仍需明确逻辑，不能只改展示数字。规则表在进入热循环前解析／校验，热点不每次按字符串查 JSON。

### 5.3 参照、哈希与兼容

- `next-pvp71` 和已冻结的 71 对拍数据继续只读。保留 B 对 A／旧 Python 71 的检验，不要修改旧参照来适配 72。
- 72 的新期望来自明确规则、独立小模型、人工可核算场景，或另建的 Python 72 参照副本。不要用待验 C++ 的输出反过来证明同一个 C++ 正确。72 优化前后还要做 C↔D 的逐刻差分；这能发现优化偏差，但不能独立证明 C 的新规则正确。
- 对拍沿用已批准的数值容差和排除项，记录首个差异 tick、字段、双方状态和 RNG 进度。平衡改动不成为放宽全局容差、忽略 RNG 或删除失败断言的理由。
- 为构建、规则集、规则 schema、回放／存档格式分别保留可识别版本。PC 与 Android 同规则应得到同一目录／规则哈希；修改一条费用或战斗规则应改变相应哈希，不能硬编码成旧值。
- 目前三条 Python 目录哈希差异涉及 `32`／`32.0` 的序列化，本产品既定范围是不与 Python 版互通。它不要求当前先重造 int／float 区分；也不允许 PvP72 的原生 PC／Android 规则不一致。
- 明确决定 71 回放如何读取、71 存档哪些可迁移，以及 71／72 房间是否拒绝互连。不同规则不能静默共局；旧回放不能悄悄按新规则重算。迁移前备份数据，保留可恢复的旧包。

AI 可以先保持旧策略来测引擎变化；若同时调整 AI，单独标明策略版本与开销。平衡变更后的合法选卡、费用判断和技能行为必须正确，不能因“AI 未优化”而读到旧规则。

## 6. 测量协议：避免再次测出无法解释的倍数

### 6.1 每个样本必须能追溯

记录源码／生成输入／规则／资源清单、编译器及选项、构建 ID、EXE／游戏库／APK SHA、设备及系统版本、场景与 seed、输入序列和后端配置。输出使用新目录，保留原始逐次数据、日志和失败过程。

剖析、功能测试、性能测量分开运行。计时样本关闭剖析、逐 tick JSON 与额外调试日志；采样器开销另记。性能测量串行，期间不编译、不跑全量、不录参照，也不运行后台 4 AI 对局。

现有 `PVZ_PROFILE=1` 支持 `PVZ_PROFILE_TREE`、`PVZ_PROFILE_ROOT`、`PVZ_PROFILE_MODULES`、`PVZ_PROFILE_FUNCS`、`PVZ_PROFILE_LINES`，实现见 [trace.cpp](../src/core/trace.cpp)。它偏重生成代码帧；类型化手写函数需要补可关闭的阶段计数／计时，或用能解析对应符号的采样工具。不要因为手写函数没有被该调用树列出，就判定其耗时为零。

### 6.2 电脑

- 同机、相同编译配置和环境，先验证当前核心拓扑／亲和性；CPU 12 是本次机器的选择，不是所有电脑的固定参数。
- 每场景／后端独立进程，至少 1 次预热、3 次有效重复，重要结论建议 5 次；交替顺序，报告中位数、范围及每次结果，不再只取最好的一次。
- 保留原生、Python＋已核验启用的 `_pvpcore`、关闭扩展 Python 三组。主产品比较使用实际带扩展的旧版；不能只挑最慢的 Python 作基线。
- 当前五场景适合步进对比；`run_battle --bench` 不派发输入计划，脚本也明确拒绝带输入的场景。要测英雄输入、合作或 4 AI，先实现并核对完整驱动，不能直接把场景名字换掉。
- 固定微场景之外，另测真实 4 AI 2v2、PvE 波次、网络房间、观战／回放和长局。记录 AI 决策耗时与模拟 tick，不能将无 AI 测试命名为 4 AI 实战性能。

### 6.3 Android：继续用终端脚本连续三场景

正式入口应支持受控配置、自动结束、唯一报告路径和真实成功／失败状态。沿用旧版“配置文件＋启动参数＋脚本拉报告”的方式，无需反复点菜单。诊断入口不执行任意 Python 代码，不在玩家正常流程暴露实现细节。

现有脚本和测试入口材料在 [performance-20261104-094702](../test_results/performance-20261104-094702/)，其中 `android/run_three_scenes.py` 和 `native-probe/` 可参考。脚本含本次包名、路径与会话连接条件，复用前必须改成显式参数并检查；不能直接当通用 PvP72 工具。后续正式候选应通过自身入口测量，测试驱动只作诊断证据。

每轮连续执行 20 普通僵尸、60 豌豆／普通混合、120 弹幕三档；每档至少预热 5 秒、采样 30 秒。正式提速结论每组至少 3 轮，并交替基线／候选顺序；另设足够长的实战观察温升、掉速和内存增长。

必须记录并核验实际生效的：

- `world_quality`、优化开关、逻辑／世界／物理显示尺寸、像素格式、缩放过滤与显示预算。探针使用临时 userdata；把质量写进真实存档不保证探针读取，必须通过诊断配置应用并回读。
- FPS 来自真实显示计数；模拟 tick、模拟倍率和按 tick 归一化的成本单独报告。p95 帧耗时来自逐帧样本，不能把三次总耗时伪装成帧 p95。
- 渲染／缩放／UI／present 各阶段，RSS 与可用时的 PSS，电量／温度／频率／性能请求及实际亲和性。条件无法对齐就标注限制，不把全部差异归给 V。
- 真实系统统计绑定与报告导出。当前原生 `resource.getrusage` 和 `export_performance` 的产品路径有缺口，应补真实实现并验证文件实际可取；不能填零或仅返回路径就算成功。
- 测量前后玩家数据 SHA，临时配置和驱动的恢复记录。无线调试地址是会话值；代理问题先检查路由，不能修改全局代理或把旧地址／配对码写进指导。

固定相同单位数量用于判断实现成本；新规则自然运行的实战用于判断体验。费用、攻速、存活时间改变后，两者负载可能不同，分开报告，不能强行投放本来买不起的单位却不披露。

### 6.4 至少保存这些指标

| 指标 | 用途与边界 |
| --- | --- |
| 总步进秒／native tick 数／ns 每 tick | 同量模拟成本；同时记录活跃单位、弹道及查询量 |
| 显示 FPS／模拟倍率／p50、p95 帧耗时 | 区分显示卡顿与游戏变慢；目标正常速率为 250 native ticks/s |
| 各阶段独占耗时、调用／分配次数、像素搬运量 | 找到回退来源，避免将包含子调用的总时间重复相加 |
| V 转换、Args／临时容器数量 | 检查热点是否真的脱离动态运行时 |
| 峰值及长局内存、快照／队列上限 | 区分 PC 工作集、私有提交、Android RSS／PSS；这些不能混写成同一个“内存”指标 |
| 正确性与异常 | 首个逐刻差异、hero guard、崩溃／超时、取消后在途任务、房间退出及重赛 |

## 8. 功能验收与临时豁免的边界

full98 的真实结果为 **204 模块／2366 次原生执行：2348 PASS、6 FAIL、12 ERROR、0 SKIP**。完整源身份为 235 模块／2562 项，另 31 模块／196 项有明确源套件归属。这些数字属于 71 基线，不是 PvP72 的固定分母，更不是原生全 PASS。

用户已授权 18 项精确临时豁免，见 [temporary-native-waivers.json](coverage/temporary-native-waivers.json)。当前工具依旧执行用例，原始结果不变，只在 ID、结果类型、详情 SHA 全部匹配时接受；`--strict` 禁用豁免。新增失败、签名变化、缺失／重复／额外身份、跳过、崩溃／超时、英雄隔离异常、执行中输入／二进制改变继续阻断。

延续这份已授权规则，不自行取消，也不把它扩成“72 仍是同名测试就免”。72 的合法平衡改动要有记录和独立期望；旧豁免详情因哈希等变化而不匹配时，先查明并报告，不自动更新指纹放行。原生 PASS、原始非 PASS、精确豁免、源套件归属和未执行分别列出。

优化验证采用分层节奏：

- 小改动：编译相关目标，验证受影响机制／图像／网络行为，跑对应对拍和局部性能；没有新变化时不反复执行所有长测试。
- 整链或阶段完成：完整对拍与英雄监控、当前版本全量身份核对、功能回归。保留 71 的 34 场景基线，72 增加覆盖实际改动的场景；不能只用旧 34 场景代表新版本完整验证。
- 发布候选：冻结后完成全量、真实 PC 入口、4 AI 2v2／PvE、联机／观战／回放、退出／重赛、快照真实线程与上限、长局与 Android 设备检查。复核 PC／APK 同规则、源码／库／资源／包 SHA，以及安装升级保留数据。

全量工具默认按物理可用内存和提交额度调度，`--workers N` 是上限，不是强行并发数；未知内存退回串行。编译仍串行。调度预算不是操作系统硬上限，不因测试变慢就改全局内存或关闭其他用户程序。

测试通过会减少人工重复排错，但不会替代触控、手感、清晰度、音效、手机热稳态或真实多人体验。交付报告写清楚“已测／未测”，不要将候选、模拟器或调试入口结果写成全部实机验收。

## 9. 阶段退出条件与交付格式

| 阶段 | 要交付的成果 | 退出条件 |
| --- | --- | --- |
| M0：可重复测量 | 版本清单、可参数化电脑工具、正式诊断入口、等像素配置 | 同版本重复结果可解释，数据与包指纹能对应 |

| M2：首条类型化链 | 权威有类型状态、明确边界、静态调用、生命周期规则 | 同规则对拍通过，动态操作和整场成本实测下降；无收益就记录并调整方案 |
| M3：72 平衡基线 | 用户修改清单、规则表、版本／哈希／兼容策略、新期望 | 新规则可独立核验，C 基线可复现 |
| M4：72 优化合流 | C↔D 正确性与性能、真实模式／长局、PC／Android 候选 | 门禁满足、差异披露、玩家数据与旧版本可恢复 |

M3 可与前面诊断／优化并行准备，不能在同一性能样本中混入未冻结的规则。整个计划按收益推进，不以完成大量局部改动数量衡量进度。

每阶段交接至少写：

```text
基线 / 候选：构建 ID、规则 ID、源码/二进制/输入清单与路径
改了什么：热点链、数据结构、调用边界或显示路径
为何这样改：当前剖析证据，哪些仍是假设
测得结果：每次原始数据、中位数/波动、整场与阶段成本、内存
保持了什么：逐刻/像素/线程/网络等相关验证与报告路径
全量口径：身份总数、PASS/FAIL/ERROR/SKIP、豁免、源归属、未执行
平衡变更：用户决定、旧新数值、合法期望变化与兼容处理
剩余事项：未测设备/模式、失败证据、下一条可直接执行的任务
```

最终应能回答两个独立问题：**相同规则下实现快了多少；PvP72 新规则在实际对局中表现怎样。** 两者都需要证据，不能互相代替。
