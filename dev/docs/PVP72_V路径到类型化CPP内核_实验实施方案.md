# PvP72：从 V 路径到类型化 C++ 内核的实验实施方案

日期：2026-11-04。

本方案落实用户要求：静态／冷路径可以保留 V；动态战斗部分大胆重建为有类型的 C++ 状态与调用链，先验证正确性、适配并重跑全量，最后进行正式性能测试。本文为实施与验收方案，尚未实现新内核或执行本轮实验。

> 防漏逻辑要求：新建权威状态和接口，不代表按功能简介重新发明原版行为。现有全量用例数量、函数调用记录和35个场景不足以证明原版全部分支已覆盖。必须先建立原版逻辑迁移清单，再逐块保真迁移、补原版机制验证，具体见第5节。

> 用户目标补充：保留原游戏卡牌的核心机制和交互；机制或数值已有PvP改动的，继承最新明确生效的PvP版本。底层更换为有类型的C++逻辑，允许agent深入优化函数块、调用链、数据结构和架构。行为保持与实现重构分别验收，不能为了提速简化卡牌行为，也不要求最终C++永久照搬Python的函数划分。

## 1. 目标与当前起点

这里的“纯 C++ 路径”指明确类型的原生数据和函数调用。V 本身也是 C++ 实现；仅有 `.cpp` 文件、换一个启动参数或把局部运算改成 `double`，不能证明动态战斗已脱离 V。

本实验的目标是：**新内核拥有权威战斗状态，完整逐 tick 热点链使用有类型的参数、存储和调用；V 留在明确的外围边界。** 实现结构可以重建，已冻结的 PvP72 规则和可观察行为保持。

编写时已核对README与发布清单：最新修复版为PvP72 R8。以下实现特点仍需开工时核对；35场景、旧全量及手机性能数值属于此前对应构建的历史证据，不能直接作为R8或新实验重新验证的结论。

实现特点与历史起点：

- [Obj 单位存储](../src/core/obj.h) 的已知字段是固定槽，但字段类型仍为 `V`；[Match 运行时](../src/sim/pyrt.h) 也大量使用 V。
- [targeting72.cpp](../src/sim/pvp/hand/targeting72.cpp) 已将部分目标几何改为 `double`，入口、单位和候选访问仍经 `V/Args`；它不是完整的新内核。
- `PVZ72_REFERENCE` 目前只切换部分目标查询和绘制实现，**不是完整战斗后端开关**，不能直接拿它证明本实验完成。
- 同规则35场景对拍已通过；72旧套件记录为204模块、2366次执行，2324 PASS／30 FAIL／12 ERROR／0 SKIP，正式旧套件验收状态为 false。新实验必须保留原始口径。
- 历史R4手机72样本约7.28／5.75／7.98 FPS，模拟倍率约1.000／0.594／0.234。此前主要收益来自显示路径，不能作为R8或新内核的性能成果。

证据入口：[72变更与验收](PVP72_变更与验收.md)、[历史安卓性能报告](PVP72_安卓实机性能测试_20261104.md)、[R8交互与存档验收](PVP72_R8_安卓交互与存档验收_20261104.md)、[发布清单](../dist/PVP72-20261104-release-manifest.json)。开工时重新核对实际最新构建及其验证范围。

### 1.1 行为依据：原版机制叠加最新PvP改动

有效行为按机制逐项确定：

```text
原版卡牌／共享系统机制
  ＋当前适用的补丁
  ＋明确生效的最新PvP机制与数值覆盖
  ＝本轮冻结的有效规则及交互
```

处理规则：

1. 用户已明确的最新规则及已核实的版本变更优先。PvP明确修改的费用、生命、伤害、冷却、目标选择、技能效果或交互，采用新行为，不能恢复成裸原版。
2. 没有被覆盖的原版机制继续保留。某卡只改了费用，不代表其攻击方式、状态反应或死亡行为也可顺便改变。
3. 机制与交互需要按行为迁移，不能只复制目录数字。包括有效目标、攻击／触发时机、伤害与护甲、状态叠加、召唤／派生、地形依赖、死亡与同刻结算，以及秘籍、英雄、队伍／模式的联动。
4. 手写C++中的最新PvP改动也是真实来源之一；不能只从旧Python或反编译文本重新生成，覆盖掉已经生效的新机制。
5. 当前实现与明确规则冲突时，记录为待核实缺陷，查来源并做专项验证；不将未确认的实现偏差自动提升为新规则。已确认的缺陷修复单独记录，不混算为性能收益。
6. “最新”在每轮开始时冻结为具体构建、规则哈希与机制清单。开发期间收到新平衡决定，独立记录并同步更新双方参照，再开始新一轮；不能让计时中的规则持续变化。

实施时形成每卡及共享机制的行为矩阵，可与第5节迁移映射关联：稳定ID、原机制、PvP覆盖项、来源版本／位置、最终有效行为、相关交互、类型化实现位置、验证场景与结果。原机制与覆盖项分列，便于检查漏继承和误回退。

### 1.2 优化权限：保留行为，深入改变实现

agent可以主动从下列层面优化，依据当前剖析决定顺序，不将工作局限于V外围的小修补：

| 层面 | 可进行的优化 | 需要保持或验证的条件 |
| --- | --- | --- |
| 函数块 | 类型推断、消除临时容器／重复读取、复用缓冲、拆分冷热逻辑、必要内联 | 条件、副作用、数值顺序及字段语义完整 |
| 调用链 | 重划函数职责，合并重复包装，有类型直接调用和处理器，批量传递上下文 | 真实执行顺序、动态覆盖边界及异常恢复等价 |
| 数据结构 | 类型化单位／地图／规则、稳定句柄、对象池、集合与索引布局 | 身份、别名、遍历／删除顺序与生命周期符合有效规则 |
| 查询算法 | 目标筛选、空间索引、洪水几何、依赖明确的缓存与批处理 | 候选集合、平局优先级、失效条件和目标身份一致 |
| 系统架构 | 重建step阶段、状态所有权、事件／命令／快照接口，减少跨层转换 | 同刻可见性、RNG消耗、回放／联机及外部读取正确 |
| 任务调度 | 评估可独立计算的工作，消除重复任务与无效等待 | 并行必须有确定性、生命周期和资源上限证据，不改变权威结果 |

保真转译是建立可靠起点，不要求最终实现永久与Python一一同形。完成来源对应和行为基线后，可逐项做结构／算法优化；保留优化前后证据，一个类型化处理器可以对应多个原版块，但来源与被消除逻辑的等价性仍须可审阅。

不允许以降低模拟频率、少处理原版分支、忽略状态／交互、减少单位能力或取消正常记录来取得收益。架构做了多少改动不是完成标准，完整行为和整场实测共同决定结果。

## 3. 划定 V 与新内核的边界

“静态／动态”按实际运行频率和状态职责划分，不等同于 C++ 的 `static` 关键字。配置里的数值虽然不变，也应在进入热循环之前转换为有类型的规则参数。

| 部分 | 目标实现 |
| --- | --- |
| 菜单、文案、配置解析、资源元数据、工具操作 | 可继续使用 V |
| 对局规则、卡牌参数、地图初始数据 | 进局时校验并转换为有类型的数据 |
| 单位、英雄、地图运行状态、弹道、冷却、效果与生命周期 | 由新 C++ 内核权威持有 |
| 原版区段、bonus_scan、targets.context、gate、目标索引、洪水寻路、命中与伤害 | 有类型参数和明确处理器，正常生产热路径不经过 V／Args |
| 输入、AI指令与战斗事件 | 明确命令／事件类型、顺序及所有权 |
| UI、联机、回放、观战读取状态 | 经可版本化的快照、事件或受控视图接口 |

建议的状态流：

```text
外围 V 配置／菜单
       │ 进局校验、一次初始化转换
       ▼
有类型规则 + TypedWorld（唯一权威战斗状态）
       ▲                          │
  有类型指令队列                  │ step / 事件 / 只读快照
       │                          ▼
输入／AI适配层              绘制、联机、回放、观战适配层
```

必须避免：

- 每个 tick 将完整世界 V→结构体→V 来回复制。
- V 世界和 C++ 世界同时可写，靠周期性同步维持两份“权威”状态。
- 外层回调读到延迟一刻的旧英雄、目标或生命值。
- 新内核未支持某单位时，静默退回旧后端继续执行并把测试计为新内核通过。

外围确有 V 转换的，记录转换时机、次数、字节量和耗时。最终整局测量必须计入这些正常边界成本，不能只展示内部循环的最好成绩。

## 4. 新内核的实施方式

### 4.1 优先路线：从现有逻辑做保真类型化转译

用户提出的“由V块找回原版板块，再转成C++”可以落实为有来源对应的类型化转译。现有工程已具备部分对应链，无需按玩法说明重新推测逻辑：

```text
原版字节码（源SHA、代码对象、区段范围）
  → 恢复的Python文本／AST
  → 当前实际执行的原版＋补丁＋PvP门控路径
  → 已生成的V语义C++
  → 同控制结构的有类型C++及权威状态
```

可复用的材料包括 [恢复的僵尸区段](../extract/original/regions/zombies.py)、[原版区段来源记录](../extract/schema/original-regions-provenance.json)、[现有转译器](../tools/py2cpp.py)、[PvP执行区段](../src/sim/gen/regions.cpp) 和 [隔离原版区段](../src/sim/gen/original_regions.cpp)。例如僵尸区段记录原始范围68412..97986，当前两个C++区段保留相应循环／条件，但PvP区段还包含 `_pvp_zombie_gate`。

来源对应目前覆盖区段／函数及部分调用点，不代表每个生成表达式都有完整自动映射；手写覆盖和72修改也需纳入清单。不能只转换裸原版 `extract/original` 后替换PvP执行路径，那会漏掉门控、补丁或新版规则。

实施时优先从已校验的Python AST或带来源身份的中间表示生成新后端，保留每个条件、循环、调用与先后顺序，同时转换：

- 单位、地图、上下文和参数的字段schema及函数签名。
- 局部变量／表达式为明确类型，单位集合为有类型集合与句柄。
- `rd/wrm` 等动态访问为有语义的类型化读写；写入拦截、缺失位、别名等行为不能随语法替换丢失。
- `call/callm/Args` 为有类型处理器与调用，正常热循环不穿回V运行时。
- Python数值、取模、整除、比较等为等价的类型化操作或必要辅助函数，不直接套用语义不同的C++运算。

类型依据来自源逻辑、调用约束和完整schema；运行采样只作补充，不能把“这几轮都是整数／字段都存在”当成永久证明。无法确定的语法、类型或动态行为列为未支持并阻断对应能力，人工补齐规则，禁止生成空实现或静默V回退。

这条路线重建类型系统、存储与接口，并保留行为来源；不只是把缩进换成花括号。语法层翻译其实已有 `py2cpp.py`，本轮需要进一步去掉动态值和动态调用。来源映射、分支验证及独立参照仍按第5节执行。

### 4.2 新建明确的后端选择

保留冻结的“当前72后端”，新增“类型化后端”。名称及参数由实现确定；目前尚没有本方案定义的完整后端开关，不要把下述设计写成现成命令。

后端选择须进入实际游戏入口、对拍入口、测试运行器及必要的子进程。每份报告至少新增或等价记录：

```text
backend_requested
backend_actual
build_id / rules_id / source_and_binary_hashes
supported_capabilities
unsupported_operations
fallback_count
typed_step_count / native_tick_count
boundary_conversion_count
```

类型化模式遇到未支持能力时，明确失败并记录原因。实验早期可以只验证支持范围，但不修改全量身份分母，也不把未支持项归为“不适用”来宣称完成。

### 4.3 先完成一个小而完整的闭环

第一阶段覆盖普通僵尸、豌豆射手、豌豆弹道、英雄和必要地图规则，从进局到连续步进、命中、受伤、死亡及清理全部走新状态。它们经过的目标上下文、gate、bonus与寻路依赖也必须真正接入。

目的不是只重写一个几何函数，而是验证下面的完整结构：

```text
初始化 → 指令 → 单位更新 → 目标／路径 → 攻击与弹道
       → 英雄／单位伤害 → 状态变化 → 生成／删除 → 对外观察
```

闭环验证后逐步补齐复杂单位、技能、秘籍和模式。不能长期停留在这个小场景，再用局部收益代表全量战斗。最终实验验收仍覆盖既有完整产品范围。

### 4.4 允许重建数据结构，同时保持规则

第一轮将“状态表示／调用方式的改造”和“行为算法的重写”分开：结构体、句柄、命令及处理器可以重新设计；原版已有语句、条件、循环、先后顺序和特殊分支应以字节码、恢复文本及可执行参照逐块迁移。每块保留来源标记和测试对应。算法合并、遍历重排等进一步优化留到保真版本验证之后，每次单独对拍；不能凭单位简介或常见玩法印象重新实现细节。

- 单位使用有类型字段、稳定 ID／代次句柄和明确生命周期；先确认语义，再按测量选择布局，不先押注某种 AoS／SoA 结构。
- 区分字段缺失、`None`、零和 False；不要因为当前采样未出现某种值就删除其语义。
- 对位置列表、共享引用和对象身份梳理实际用途，建立等价别名／视图，不无条件改成互不关联的副本。
- 保留更新、目标候选、平局选择、死亡和生成顺序；直接用换位删除可能改变后续行为。
- 建立统一的英雄／单位写入入口，覆盖吞咬、伤害、灰烬、冻结等，防止再次绕过 HeroProxy 的既有语义。
- 目标上下文在正常、嵌套和异常退出时均恢复；缓存依真实地图、阵营、目标及规则变化失效。
- 使用与参照相符的数值精度和计算顺序；不顺带启用 fast-math、改 float、并行归约或改变随机消耗顺序。
- 固定 gate 使用有类型处理器；确需覆盖的行为提供真实 hook 和缓存失效。正常路径不再反复构造闭包、Args或按字符串查字段。
- 延续快照冻结、线程所有权、取消后在途计费和资源上限。不能把当前非线程安全的 V 引用对象直接变为可变跨线程共享数据。

建议新增独立的内核模块和构建目标，例如 `src/sim/typed/`，具体命名待实现；生成代码改动仍须有生成规则或明确覆盖层，不能依赖下次生成就丢失的手改。

AI与渲染也需明确边界：第一阶段可以使用确定指令测模拟内核；最终必须另测真实AI决策与完整显示。若AI内部仍使用V，就如实说明剩余范围，不能宣称整款游戏所有动态代码均已脱离V。

## 5. 正确性：同规则、双世界、逐刻对拍

### 5.1 双世界与可观察结果

建立两份彼此独立的世界：各自的状态、随机数生成器、事件队列、缓存和生命周期，从相同规则、种子及指令创建。不能在同一个可变世界上执行两次 step 来模拟双后端对照。

对拍通过共同的可观察状态 schema 比较：

- 单位／英雄位置、生命、效果、冷却及归属。
- 目标 ID、单位顺序、生成／死亡／删除事件。
- 地图与障碍变化、经济资源、命令执行顺序和模式状态。
- RNG状态与消耗进度。
- 回放、快照和联机需要的事件及版本身份。

沿用当前批准的 `1e-9` 容差与已有地址排除项，不因重构困难全局放宽。第一处差异应输出 tick、字段、双方状态、相关指令和随机进度。

复用现有35个同规则场景，并补充新结构风险：稳定句柄回收、同刻死亡／生成、英雄拦截、嵌套上下文、别名写入、缓存失效与重赛。新增验证针对真实风险，不只检查新实现自己设置的标志位。

小闭环可以使用受影响场景先定位问题；能力补齐后必须跑完整对拍。未支持项、崩溃和差异保留原始记录，不能只保留成功场景。

### 5.2 原版逻辑要有独立的迁移清单

当前材料的含义必须分清：

- [旧测试对照表](coverage/旧测试到C++覆盖对照.md) 主要描述旧测试模块及断言迁移，且保留历史状态；不是原版代码分支覆盖报告。
- [step_coverage.py](../tools/step_coverage.py) 在五类参考场景、各60次step中记录函数调用次数和源码行数。[已有结果](../extract/schema/step_coverage.json) 证明函数被调用过，不能证明函数里的每个分支执行过。
- [verify_decompile.py](../tools/verify_decompile.py) 比较规范化的非控制指令多重集，明确跳过跳转、循环等控制指令。它不能独立证明控制流、语句顺序和全部分支行为正确。
- [原版区段来源记录](../extract/schema/original-regions-provenance.json) 与 [补丁来源记录](../extract/schema/original-patch-provenance.json) 可复用来核对来源及版本，但“已生成／无翻译TODO”不等于运行期全部分支已验证。

因此，先清点当前产品模式相关的原版主模块区段、函数／嵌套代码、运行时门控和补丁调用。静态可能可达但未被现有场景触发的部分仍须保留。不能把“已有提取文件列表”直接当作原版逻辑全集，也不能把未命中的分支擅自视为死代码。

实施时新增机器可读的原版逻辑映射，例如 `docs/coverage/original-logic-map.json`，并生成便于审阅的摘要。当前本文没有创建或填充这份覆盖成果。每项至少包含：

| 字段 | 内容 |
| --- | --- |
| 来源身份 | 原始字节码／补丁／运行时注入层、SHA、代码对象名与区段／偏移范围 |
| 原版逻辑 | 恢复文本位置、条件与分支、读写状态、调用及特殊副作用 |
| 现有实现 | 当前V后端对应函数、已知修正和72规则变化 |
| 新实现 | 类型化函数／处理器位置，字段与操作的对应关系 |
| 验证 | 触发条件、场景／用例ID、基本块和分支记录、逐刻差异结果 |
| 状态 | 未盘点／未迁移／已迁移未触发／已触发但未断言／已验证／有依据的范围外 |

代码对象及偏移记录须绑定源SHA；原始字节码与注入后的字节码分别标识，不能混用偏移。处于范围外的项说明所属功能和依据，不以“测试没用到”作为理由。

### 5.3 先补原版机制，再扩充场景数量

在参考执行、V后端和新后端中加入可关闭的基本块／分支记录，以逻辑映射关联结果；正式性能计时关闭这些记录。分母来自源逻辑盘点，未触发项仍显示，不能只统计成功执行过的代码。

围绕原版机制建立触发矩阵，而不是只增加新内容的测试名称：

- 单位完整生命周期：部署／成熟、攻击前后摇、受伤、护甲变化、死亡、生成和清理。
- 状态及临界点：冻结／减速、灰烬、魅惑、睡眠／唤醒、血量与冷却阈值、缺失字段与零值。
- 场地与移动：陆地／水面／支撑、飞行与落地、地图边界／环绕、障碍改变及寻路失效。
- 交互顺序：同刻多次命中、护甲脱落后的伤害、死亡壳层、召唤与删除、戴夫代理写入和上下文切换。
- 相互作用：按源逻辑确定相关的状态、单位、地形组合，补关键双因素与多阶段组合，不能只做每张卡单独出场的冒烟。

上述是分类，具体机制以源逻辑盘点为准，不凭分类猜造游戏规则。跨越冷却、成熟、死亡等阶段需要足够的模拟长度，短时能启动不等于生命周期完成。

再加入可重复的差分生成测试：从合法初态或可达指令序列生成边界状态，固定seed，让双方使用相同输入逐刻比较；失败保留seed、轨迹及最小化复现。尽量覆盖此前未命中的分支，而非只随机增加普通单位。

### 5.4 参照独立性与防漏门禁

V后端提供广泛的可执行参照，但它也可能有翻译遗漏。原版未被72修改的机制，使用实际CPython原字节码／既有原版执行路径做针对性第三方核验；涉及72修改的机制，绑定用户规则和独立专项期望。不要把待验C++输出录成唯一标准答案，也不要修改冻结的71参照来消除差异。

复用已有原版执行与参照采集工具，按需补齐输入规范化；Python仅用于离线验证，不作为新内核的运行依赖或隐藏回退。

每种关键机制做代表性的负向控制，例如临时禁用一次护甲、冻结或死亡分支，确认对应断言／差分确实失败，恢复后复核源码指纹。单纯记录“分支访问过”不能代替结果断言。

进入E3验收时：

1. 目标范围的原版逻辑已有可追溯盘点；未知、未迁移和未触发项分别列出。
2. 没有未解释、尚可能可达却缺少新实现对应的逻辑块；高风险伤害、生命周期、状态组合和顺序分支已有触发与结果证据。
3. 其余未覆盖项给出具体风险及限制，无法支持完整范围时继续阻断完整验收，不能仅凭旧全量绿色放行。
4. 同时提交原版逻辑覆盖报告、原有全量结果和新增机制验证，分别给出分母。即使行／分支覆盖达到100%，也不声称所有状态组合或路径已经穷尽。

## 6. 全量测试：需要再次适配什么

**需要接入新后端、调整部分夹具与内部访问，并重新执行全量；不需要重新翻译或重写全部业务断言。** 适配工程量可能不小，主要集中在测试边界，不能靠复制旧结果代替执行。

| 原测试类型 | 处理方式 | 验收重点 |
| --- | --- | --- |
| 检查伤害、费用、胜负、目标、存档／回放等外部行为 | 保留业务断言，参数化运行两个后端 | 同规则结果一致，实际执行后端可证明 |
| 直接构造或修改 V 单位／世界字段 | 接有类型构造器、受控测试访问器或权威状态视图 | 修改实际进入新状态，没有另一份测试专用影子世界 |
| 替换方法、`patch.object` 和回调 | 接真实有类型 hook；必要兼容转换只发生在注入边界 | 替换后的函数真正被调用，生产路径仍走新实现 |
| 读取对象内部布局或实现细节 | 评估其保护的行为，保留等价断言与可观察接口 | 不能仅因内部重构就删除有效行为要求 |
| 已明确归属CPython的内省／源码专属断言 | 延续原归属和独立验证 | 不借本实验扩大排除范围 |
| UI、联机、观战、回放和应用入口 | 工具可能可复用，但要传递新后端并重新验证 | 不能入口选了typed，实际房间仍创建旧世界 |

测试桥可以把测试输入转换为命令／状态构造操作；运行期间的写入需要明确生效时机。不能让测试接口每刻重新导入完整 V 世界，使测试路径与真实产品路径脱节。

后端接入应先少量验证，再推广到全量：

1. 核对实际收集的模块和用例身份，输出每个后端的执行范围。
2. 在同一组代表测试上证明旧后端和新后端都真实执行。
3. 做负向控制：临时让新后端某个伤害／目标结果产生可识别偏差，确认相关断言与对拍失败；恢复后重新核对源码指纹和结果。
4. 再将完整套件接入新后端。检查主程序、测试程序、子进程和房间实例的实际后端；没有切到新内核的项不得算成其通过。

历史72旧套件42项非PASS已有分类，其中15项与71原结果相同，27项审阅为72规则／身份变化；这不是42项已经被豁免。实验开始时重新核对最新执行材料，再冻结逐例结果、详情签名和审阅材料，阻止原PASS退化与新增未解释变化。

[18项临时精确豁免](coverage/temporary-native-waivers.json) 保持既有授权边界，不自动改ID、失败类型或详情指纹；`--strict` 继续保留。修复项恢复PASS如实记录，不能通过扩大豁免获得“新内核全通过”。

每阶段分别报告：收集总数、实际执行、PASS／FAIL／ERROR／SKIP、未支持、未执行、已有差异、精确豁免、新增退化与后端不匹配。保存逐例身份对应，不只比较汇总数字。

旧全量在此保护已有产品行为和新内容；第5节的原版机制／分支验证补足其覆盖盲区。两套证据共同验收，不能互相替代。新增用例独立列出，不能靠合并计数掩盖旧用例被删除或原版分支仍未验证。

## 7. 阶段目标与退出条件

| 阶段 | 交付物 | 退出条件 |
| --- | --- | --- |
| E0：冻结与接线 | 当前72基线、原版逻辑盘点、规则／源码／二进制清单、双后端标记、支持范围 | 原版清单与盲区明确，两边可独立启动，基线可复现 |
| E1：有类型小闭环 | 原生权威状态、保留来源对应的完整基本战斗链、机制测试 | 支持范围内逐刻一致，关键原版分支有触发／断言，静默回退为0 |
| E2：扩展机制与测试桥 | 更完整的单位／技能／模式，有类型hook和状态访问、分支差分场景 | 相关回归通过，逐块迁移对应及负向控制证据完整 |
| E3：全功能正确性 | 原版迁移／覆盖审计、完整对拍、全量逐例审计、真实入口／联机／快照等验证 | 第5节防漏门禁满足，无新增未解释退化，V热环依赖审计完成 |
| E4：正式性能实验 | 电脑与手机重复样本、完整成本与内存、结论 | 同规则、同工作量、版本可追溯；收益或无收益均如实交付 |

E1／E2可以做少量定点计时发现设计问题，不将其作为最终成绩。**正式性能对比在E3之后运行。** 如E3仍有未解决阻塞，只能发布明确标注的探索性测量，不能宣称完成后的性能验收。

E3需核实正常 `step` 内是否仍有 V字段访问、动态调用、Args构造和旧后端调用；结合代码依赖、调用计数与剖析确认。少量局部 `double`、自报一个 `typed=true` 或只检查编译成功都不足以通过。

## 8. 最后的性能测试怎么做

### 8.1 主比较对象

主比较为：**冻结的当前72后端 ↔ 相同72规则的类型化后端**。绘制优化、质量、资源、AI策略和记录功能保持一致，单独切模拟后端，避免混入本轮以外的收益。

旧Python＋C++版本可保留为体验参照；若规则不同，单列说明，不将其差异当作纯类型化倍数。

### 8.2 分三层测量

1. **内核：** 确定输入和相同native tick区间，测总步进、每tick成本、分配次数／字节、峰值内存、V边界转换与fallback。关闭逐刻JSON及额外剖析后计时。
2. **应用：** 使用真实正式入口，测显示FPS、正常模拟倍率、p50／p95帧耗时、绘制／缩放／present及正常回放成本。
3. **实战：** 4 AI 2v2、PvE、联机／观战／回放、退出／重赛和长局，记录AI决策、队列、温升及内存增长。

电脑纯步进不能代替真实窗口FPS，测试进程工作集不能代替完整游戏占用；PC峰值工作集、私有提交与手机RSS／PSS分别标注。

### 8.3 电脑协议

- 串行计时，期间不编译、不跑全量、不录参照、不运行后台4 AI对局。
- 相同机器、工具链与构建选项，核验核心拓扑及实际亲和性；CPU12只是此前这台机器使用的选择。
- 每场景／后端至少1次预热、3次有效独立进程，重要结论建议5次；交替顺序，报告中位数、范围和逐次原件。
- 原五个步进场景加类型化链专项。现有 `--bench` 不派发输入计划，带英雄输入／AI指令的场景须先实现并验证驱动。
- 复用 [benchmark_pvp72.py](../tools/benchmark_pvp72.py) 的清单与漂移检查思路，扩展完整后端参数；不删除SHA门禁，不假定当前脚本已经支持新内核。

### 8.4 手机协议

- 采用正式APK诊断入口和终端脚本，连续20普通、60混合、120初始单位弹幕三场景；每档预热5秒、测30秒，每组至少3轮，尽量交替后端。
- 配置并回读实际原画、过滤、优化开关和逻辑／世界／物理尺寸；不能只修改玩家真实设置而忽略探针临时userdata。
- 记录实际存活单位／弹道与模拟进度。“120”若只是初始投放，报告不能写成持续120单位并存。更新成本另按相同tick区间核对。
- 保证测试指令确定，记录额外部署或外部输入；出现负载偏离的样本标记原因并复测，不静默删除，也不按严格固定场景统计。
- 正式计时关闭额外分配／绘制计数；路径命中与计数另起一轮，不把补测失败记为通过。
- 记录电量、温度、频率、性能请求／亲和性和后台限制。短样本结论不外推为热稳态，另做长局。
- 核验APK／库／资源／规则身份及升级实际读取的新资源；当前72实机曾发现旧资源覆盖问题，不能只看versionCode就判断加载正确。

手机当前由用户使用。本文不授权立即占用设备；设备可用时再安排该阶段，不复用历史无线调试地址、配对码或擅自改变全局代理。

### 8.5 如何判定有收益

同时检查：每tick成本、正常模拟倍率、FPS／长帧、正常边界转换、内存及真实模式。不给“少推进模拟”“少画可见物体”“关闭回放”“减少单位”等变化记作相同条件下的收益。

历史R4手机混合／弹幕每tick约4.88／9.89ms，满速250tick/s平均只有4ms总预算；这些历史值不能替代最新构建的复测。不能承诺重写后自动达到某个FPS或固定倍数。

若整场收益仍小，定位剩余耗时与边界成本，报告真实结果并决定下一条链。负结果也是实验结论，不以局部微基准替换整场结果。

## 9. 最终交付与接手清单

交付至少包括：

- 独立实验实现、构建方式与回退选择；当前正常发布包和玩家数据保持可用。
- 双后端能力矩阵、权威状态／接口／生命周期说明、剩余V边界及调用统计。
- 原版源逻辑到新实现的迁移映射、基本块／分支覆盖与未覆盖清单、机制矩阵及独立参照核验。
- 同规则对拍、负向控制、完整全量逐例归属与差异报告，全部失败原件。
- 真实PC入口与模式验证；必要的APK候选及明确的设备验收边界。
- 正式性能报告、逐次原始数据、环境配置和可复现的清单／哈希。
- 新增源码、生成规则、测试桥和工具变更的说明；不将本实验顺带打包为完整开发者发行物。

下一位开发者从E0开始，先完成后端标记和一个真实闭环，再扩展全功能。每次交接写明当前支持范围、首个差异、实际执行后端、已完成的验证，以及下一步可直接执行的任务。
