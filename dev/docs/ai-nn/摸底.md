# 摸底（第 0 步）

2026-11-12，分支 `ai-nn/foundation`。环境：Linux x86-64，g++ 13.3，2 核 Xeon 2.1 GHz，没有 SDL2 开发包，不能装包。下文的行号指本分支起点（`1c28636`）的源码。

结论先说：无头环境可以不链接 V 运行时；1v1 的 AI 节拍能从源码逐条确定；内核里没有会影响对局的跨对局全局可变状态；规格里的数字全部核对无误；AI 只在房主一侧计算。另有两个顺带发现需要开发机确认（第 5 节）。

## 1. AISeat 的精确节拍

权威实现：`tools/pvp72_sources/lobby_room.py` 的 `class AISeat`（第 100 行起）和 `battle_tick`（第 310 行起）；类型化分支在第 350–368 行。

| 项目 | 源码事实 | 无头驱动的做法 |
| --- | --- | --- |
| 帧内顺序 | `App.step`（`app.py` 2859–2865）先 `ai_room.tick(dt)`，再 `room.update(dt)`。`AIRoom.tick`（`lobby_room.py` 551–552）按 `seats` 字典顺序逐个 `safe_tick`。`Room.update`（`room.py` 1159–1166）按真实时间累加，一帧推进 0 到 12 个房间 tick | 每个房间 tick 之前，各 AI 席位各有一次行动机会，然后 `step()` 一次。这等价于稳定不低于 30 帧的游戏；低帧率时游戏里 AI 的机会更少，无头不模拟 |
| 控制间隔 | `if b.time < self.next_ctl: return`，然后 `self.next_ctl = b.time + 1/HZ`（347–349 行）。`DESKTOP_CONTROL_HZ = 15.`，`ANDROID_CONTROL_HZ = 10.`（34–35 行） | 同样的两行浮点运算；`--control-hz` 默认 15 |
| 重规划间隔 | `every = getattr(agent, 'plan_every', 2.)`（357 行）。r22 的继承链里 `rv_r7.Agent.plan_every = 1.5`（`src/ui/gen/pm_rv_r7.cpp` 67 行；`rv_r2` 的 2.0 被它覆盖）。`replan = self.plan is None or b.time - self.plan_at >= every`（358 行） | `plan_every = 1.5`，同样的判断 |
| 计划校验 | 重规划后 `self.plan = validate_plan(raw, deck)`；抛 `ValueError` 时 `self.plan` 保持原值，`plan_at` 照常更新（360–367 行）。所以第一份计划就不合法的话，每个控制 tick 都会重规划 | 驱动里的 `plan_valid` 实现了 `validate_plan` 中能拒绝类型化计划的条件：`priority` 是卡组里的非秘籍卡；配额键在卡组里、值是 0 到 700 的整数；`teleport_hp` 有限。r22 的计划始终合法，实测拒绝次数见 `进度.md` |
| 一次 AI tick 的内部顺序 | `TypedBattle` 的 `ai_tick`（`typed_battle.cpp` 588–604）：`ai_observe(seat, match_id)` → 需要重规划时 `ai_plan(seat, ai_controller_recovering(seat))` → `ai_control(seat, "r22", send)` | 相同顺序，直接调 `Session` 的这三个接口 |
| `recovering` 的来源 | 调 `ai_plan` 时读控制器当前的 `is_recovering()`，也就是上一次控制 tick 结束时的值 | 相同 |
| 指令出口 | `AISeat.send`（147–151 行）组出 `dict(type=kind, seq=self.seq[seat], **data)`，`seq` 从 1 起每次加 1；经 `Room.command` 的 `input` 分支（`room.py` 694–702，只检查处于战斗阶段且未暂停）到 `battle.command_input`；`TypedBattle` 把 V 字典用 `%.17g` 打成 JSON 文本再解析（`typed_battle.cpp` 25、474–481 行；`core/value.cpp` 618–622 行），然后 `Session::command` | 直接调 `Session::command`。数字按同样的 `%.17g` 规则转换（整数值成为 JSON 整数）；`seq` 默认从 1 起（`--seq-base`） |
| `match_id` | `room.match_number`，房间第一局为 1（`room.py` 36、691 行），只写进观测 | 固定传 1 |
| 重置时机 | `ensure_agent`（160–183 行）在 agent 为空或 `agent_key`（房间、地图、种子、地形哈希、席位、局号、选卡表）变化时重建 agent：`reset_observation()`（`next_ctl=0`、`plan=None`、`plan_at=-1e9`，并调 `reset_ai_observation`），再调 `reset_ai_planner`、`reset_ai_controller`。新对局对象出现时 agent 置空（339–342 行）。暂停恢复后只做 `reset_observation`（343–345 行） | 每局新建 `Session`，各席位的观测器、规划器、控制器本来就不存在，等价于开局重置。不模拟暂停 |
| 异常处理 | `safe_tick`（199–219 行）捕获异常：写诊断文件，按真实时钟退避 `min(5, 0.5·2^(n-1))` 秒，`reset_observation`，连续 3 次后重建 agent，并发一条 `move=0` | 无头没有真实时钟：AI 抛异常时终止该局，在结果行写 `ai_error`。实测次数见 `进度.md` |
| AI 补贴 | `ai_subsidy_seats` 只在合作（`room.py` 1076 行）和 2v2（1094 行）设置；1v1 的 `_start_battle` 不设置 | 不调用 `set_ai_subsidy_seats` |
| 1v1 里谁是 AI | 固定 AI 房 `SLOTS = ('main', 'spare')`（25 行）：平时只有 `main` 入座，人机对战；房主观战时 `spare` 也入座，双方都是 AI（537 行）。房主也可以邀请 AI（`app.py` 1294 行） | 植物、僵尸都由 AI 控制 |
| 席位先后 | 游戏按 `seats` 字典的插入顺序（先 `main` 后 `spare`），和阵营没有固定对应 | 默认先植物后僵尸，`--seat-order` 可换。顺序对结果的影响见 `进度.md` |

投降：`battle_tick` 开头的投降逻辑（312–333 行）只响应队友发起的请求，1v1 没有队友，不会触发。

## 2. 跨对局全局可变状态

检查范围：类型化内核（144 个 `.cpp` 及其头文件）、`session.cpp`、`ai_planner_r22.cpp`、`ai/`、组合层 `match_probe.cpp` 和两个 `.inc`。方法：grep `static`、`thread_local` 和命名空间级变量定义，逐条看。

| 位置 | 内容 | 是否影响对局 |
| --- | --- | --- |
| `composition/match_probe.cpp:41` | `int trace_budget=6` | 否。只在 `_WIN32` 且开启 `MATCH_TRACE` 时用于调试追踪 |
| `sim/typed/room_transport.cpp:38` | `static std::once_flag`（Winsock 初始化） | 否。联机传输，对局逻辑不经过 |
| 其余 `static` | 全部是 `static const` / `constexpr` 表，以及静态成员函数 | 否。只读 |

另有两点：

- `TypedSession` 给对局装了真实时钟（`session.cpp` 22 行的 `wall_clock`）。它只用于 `room_scheduler.cpp` 139–143 行的 `native_cost_ratio`，这个值只有闯关导演读取，1v1 没有导演。
- 没有找到 `thread_local`，也没有非 const 的命名空间级变量。

静态检查的结论是同一进程可以连续跑多局。实测结果（同进程 10 局对比 10 个独立进程）见 `进度.md` 第 2 步。

## 4. 联机

- AI 席位只存在于房主进程：`AIRoom` 由 `lobby_room.create()`（先 `app.create_offline_host()`）或房主邀请时创建，挂在 `app.ai_room` 上，由 `App.step` 驱动。
- AI 的操作和人类输入走同一个入口：`Room.command` 的 `input` → `battle.command_input`，会进对局日志。`replay.py` 开头写明回放是"输入录像，由真实的 NativeBattle 重放"，`INPUT_FIELDS` 列出了被录的字段。
- 客机不重算对局：`app.py` 1045 行起，`guest` 收到 `room_snapshot` 后 `merge_view`。

所以网络推理的浮点差异只会影响房主产生哪些指令，不会让两端不同步，回放重放的也是指令。没有做的：没有通读全部联机代码，观战和断线重连路径没查。

## 5. 顺带发现

1. **类型化对局里禁卡列表恒为空（请开发机确认是否有意）。** 冷数据 `cold.json` 里没有禁卡列表，`match_probe.cpp` 也没有给 `deployment.bans` 赋值的代码（全文件只有 `unit_card_memo` 那一处出现 `bans`）。而 Python 的 `NativeBattle` 持有 `self.bans`，`resolve_card(key, secrets, bans, night)` 会用它拒绝被禁的卡和派生形态（`native_battle.py` 1571–1574 行）。卡组本身不会含被禁的卡，所以平时看不出差别；可能出差别的是对局内才决定的卡，例如模仿者复制一张被禁的卡。数据集里 144 局带禁卡。我没有构造场景验证，这只是读代码得出的。
2. **冷数据进入会话时键顺序会变。** 门禁程序把 `cold.json` 解析成保序的 `ordered_json`；会话路径经过 `nlohmann::json`（键按字典序）再转成 `ordered_json`。实测两条路径结果一致（`进度.md` 第 1 步），目前没有观察到影响。
3. **SDL 只在一处被内核用到**：`native_art.cpp` 的 `NativeArtStore::pixels()` 用 `SDL_SoftStretch` 缩放精灵。本环境没有 SDL，无头构建用 `build/ai-nn/sdl_shim` 里重写的同名函数。这个缩放函数在实测对局中的调用次数见 `进度.md`。
4. **组合层新鲜度检查没有结论。** `python3 tools/typed72/make_app_composition.py --check --out src/sim/typed72_app/composition` 在本环境输出 `checked 0 files`，没有证明组合层和来源一致。
5. **浮点。** 无头构建沿用安卓的选项 `-O2 -ffp-contract=off -fno-fast-math`。`sin`、`cos`、`pow` 这类数学库函数在 glibc 和 MSVC 运行库之间可能有末位差异，本环境无法验证，要靠开发机对拍。
