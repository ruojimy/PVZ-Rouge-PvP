# PvZ PvP AI 神经网络化：基础工作规格

Nov 12, 2026 · @ruojimy

> **勘误（11-12，按开发机源码核对）**：本文写于只有开发者包、开不了局的环境，其中"开局数据只能由游戏开局时现场生成"不成立。`build/typed72-match-v1/cold72_export.cpp` / `build/pvp73-tools/cold73_export.cpp` 早就能把一局的冷数据、图集像素和绘制图集导出成文件，`match_probe.cpp`（`typed72_match_gate`）直接读这些文件跑类型化对局，不经 V。现已导出 216 局 1v1 开局数据集，放在 `build/ai-nn/cold-corpus/`，说明见 `build/ai-nn/README.md`。图集与地图、卡组无关；种子会改变地形，所以不能只改种子。

## 结论

训练前要补齐 7 项基础工作，前 5 项是必需的，后 2 项可以后置。最大的障碍不是网络本身，而是**现在开一局对局离不开动态运行时和图片资源**，所以第 1 项决定了后面所有事能不能批量跑。

| 序号 | 工作 | 产出 | 验收标准 |
| --- | --- | --- | --- |
| 1 | 开局数据落盘 | 每张地图一份冷数据文件和载入器 | 从文件载入的对局与现场构建的对局逐 tick 对拍一致 |
| 2 | 无头对局驱动 | 不经 V、不开窗口的 AI 对 AI 循环 | 同种子两次运行日志摘要相同；与游戏内 AI 对局逐 tick 一致 |
| 3 | 卡牌特征表导出 | 232 行数值特征加卡表哈希 | 行数与卡表一致；哈希写进文件头 |
| 4 | 规划记录器 | 每次重规划写一条（输入事实，计划，局末胜负） | 用记录里的输入离线重算 r22，计划逐条相同 |
| 5 | 规划器接口 | r22 与网络版可互换的统一接口 | 换接口后 r22 对局逐 tick 不变 |
| 6 | 评测台 | 固定种子、地图、卡组的对手池对局 | 输出分阵营胜率和置信区间；r22 自对弈结果可复现 |
| 7 | 状态复制 | 从任意时刻分叉对局 | 分叉后与原对局逐 tick 一致 |

顺序是 1 → 2 →（3、4、5 并行）→ 6，第 7 项在需要搜索或价值引导时再做。

## 现状核对

类型化内核和 AI 控制器本身已经具备训练环境的大部分条件，缺的是开局和调度这两层外壳。下表来自 PvP73 开发者包源码。

| 项目 | 现状 | 位置 |
| --- | --- | --- |
| 战略规划器 | r22，188 行手写阈值；输出计划字典 | `src/sim/typed72_app/ai_planner_r22.cpp` |
| 战术控制器 | 约 2650 行；从计划字典读取 62 个标量键 | `src/sim/typed72_app/ai/` |
| 规划器实际设置的键 | 27 个；另有 37 个控制器键从未被设置，始终取默认值 | `session.cpp` 的 `plan_dict` |
| AI 调度 | `AISeat` 仍在 Python 源翻译层；桌面 15 Hz、安卓 10 Hz 控制，`r22 每 1.5 秒`重规划 | `tools/pvp72_sources/lobby_room.py` |
| 对局内核 | 类型化，30 tick/s；`Session` 接口声明无 V 依赖 | `src/sim/typed72_app/session.h` |
| 开局数据 | 由 V 构建的 `NativeBattle` 导出，含图集像素（粒子采样读精灵 alpha，会进入权威随机数） | `cold_export.cpp` |
| 随机数 | MT19937 复刻，状态可读 | `Session::rng_state()` |
| 卡表 | 232 条：植物 61、僵尸 61、秘籍 82、经济 9、工具 9、派生 10；47 种行为类型 | `cold_catalog_data.cpp` |
| 状态快照 | 只有面向界面的 JSON 投影，没有复制或恢复 | `Session::snapshot()` |

**Linux 可移植性。** 我用 g++ 13 对类型化内核的 144 个源文件和 AI 控制器的 4 个源文件做了语法检查，147 个通过。唯一失败的是 `native_art.cpp`，原因是缺 `SDL.h`。规划器 `ai_planner_r22.cpp` 单独检查也通过。这只是语法检查，没有链接，也没有运行。

**没能做到的。** 我没有跑起来任何一局对局：开局依赖 V 运行时和图片资源，开发者包不含图片。因此内核吞吐（每秒 tick 数）没有实测值。

## 规划器网络的输入

输入分五块，大部分字段直接来自 `AiPlannerInput`，标了“补”的字段来自控制视图 `ai::View`，最后一块是规划器自身的记忆。记录器落盘的是原始事实，归一化和编码在训练端做，这样改编码不用重跑对局。

| 块 | 原始字段 | 编码 |
| --- | --- | --- |
| 全局 | `time`、`width`、`recovering`；补 `map_night`、`deathmatch` | 时间除以 600 秒并截断，另加“是否过 405 秒”（r22 的 LATE 常量）；其余为 0/1 |
| 双方英雄 | `me`、`foe` 的 `x`、`y`、`hp`、`max_hp`、`resource` | 血量比；资源除以 1000 并截断；敌方相对己方的环绕距离（地图左右相连，用 `wrap_delta`）除以半个地图宽 |
| 单位集合 | 每个 `AiUnitView`：阵营、位置、`hp`、`max_hp`、速度、`mobile`、`awake`、`grave`、卡牌 | 每个单位一个向量：相对己方英雄的环绕横距、纵距、血量比、各标志位，拼上该卡的特征行；敌我两组分别经同一个小网络后求和与取最大 |
| 己方卡组 | `deck`；补 `Player.cooldowns` | 每张卡：卡特征行、剩余冷却、场上己有数量、当前资源是否够费用 |
| 规划器记忆 | r22 的 `mode_`、`last_pressure_at_`、`last_attack_at_`、`peak_econ_`、`peak_graves_` | 上一次输出的模式；距上次受压、距上次打到对方英雄的秒数；两个峰值 |

三点设计理由：

- **单位用集合编码，不用固定槽位。** 单位数量不定，地图是横版平台而不是格子。“共享小网络加池化”在 C++ 里手写前向计算只要几十行。r22 现在用的压力值、火力数、生产者数都是这种求和的特例。
- **记忆显式喂入，不用循环网络。** 前馈网络的推理是确定的，模仿学习时每条记录也能独立使用。
- **第一版输入必须是 r22 所见信息的超集。** 否则模仿 r22 时会有学不出来的部分。

## 规划器网络的输出

输出就是现有的计划字典，第一版只接管 r22 已经在设置的键，战术控制器一行不改。所有数值键都离散成若干档，网络对每个键输出一个分类：模仿学习用交叉熵，推理取最大值，结果确定。

下面的“建议范围”是我按 r22 常量和控制器默认值推的包络，不是从对局数据得出的，需要你按对游戏的理解修正。

### 两个阵营共用

| 键 | r22 取值 | 建议输出 |
| --- | --- | --- |
| `mode` | 植物：`defend` 或 `siege`；僵尸：仅在英雄低血时设置 | 植物二选一；僵尸第一版沿用 r22 规则 |
| `teleport_hp` | 0.7 | 0.3 到 0.9，7 档 |
| `quotas` | 植物默认 30，经济与一次性卡 2 到 6；僵尸默认 60，个别卡 1 到 4；资源过 700 时抬到 16 | 每张卡一个分类：1、2、3、4、6、10、16、30、60 |
| `priority` | 植物：卡组顺序；僵尸：卡组顺序去掉墓碑 | 每张卡一个分数，按分数排序 |

### 第二版可以接管的键

控制器还读取 37 个规划器从不设置的键，例如 `threat_dist`、`cluster_value`、`cannon_value`、`kite_radius`、`rush_pressure`、`wave_min_gap`、`flank`。它们现在是写死的战术阈值，网络可以随局面调节，而且同样不需要改控制器。建议在第一版超过 r22 之后再加，每次加一组并单独评测。

### 时序

训练和评测统一用 r22 的 1.5 秒重规划间隔和 15 Hz 控制频率；发布前再用安卓的 10 Hz 复测一遍，因为控制频率变了，同一份计划的执行效果会变。

## 卡牌特征表

网络只看卡的数值特征，不看卡名或编号，这样改费用、加新卡之后旧模型仍然有合理输出。特征表从 `ColdCard` 导出，每张卡一行。

| 特征组 | `ColdCard` 字段 | 编码 |
| --- | --- | --- |
| 基础数值 | `cost`、`cooldown`、`damage`、`interval`、`range`、`speed` | 费用、伤害取 log(1+x)，其余除以固定尺度 |
| 可选数值 | `hp`、`armor`、`splash`、`explosion_damage`、`yield_amount`、`period`、`squad_count`、`reach`、`fuse` | 同上；缺省记 0，并给 `hp` 加一位“是否有值” |
| 标志位 | `producer`，以及 `anti_air`、`aquatic`、`flying`、`lob`、`pierce`、`homing`、`metal`、`vault`、`burrow` 等 38 个可选标志 | 0/1 |
| 行为类型 | `behavior`，共 47 种 | 独热，或 8 维可学习嵌入 |
| 类别与阵营 | `category`（6 种）、`side` | 独热 |

两条规则：

- **用解析后的卡，不用原始卡表。** 秘籍、禁卡和昼夜会改卡的数值，对局中应调 `ColdCatalog::player_card` 或 `unit_card` 取当前生效的值。PvP73 修复的“夜晚产出周期仍按白天算”就是用了未解析卡表造成的，特征表不要重犯。
- **文件带版本。** `ColdCatalogData` 已有 `catalog_hash` 和 `rules_hash`，导出时写进文件头；模型文件记录训练时的哈希，运行时不一致就回退到 r22。

82 条秘籍在第一版不单独编码，只通过它们对卡牌数值的改写进入输入。`ai_human_prior` 里的 158 条逐卡残差只用于选卡模型，不进规划器输入。

## 状态复制

对局状态现在不能直接拷贝，但模仿学习和第一轮强化学习都不需要它，建议后置。

不能拷贝的原因：对局主体 `MatchProbe` 是一个同时实现十个左右服务接口的结构体，成员之间互相持有引用，还带有 `std::function` 和 `unique_ptr`。按值复制会让副本里的引用仍指向原对局。

| 方案 | 做法 | 改动量 | 适用 |
| --- | --- | --- | --- |
| A 重放式 | 同一份冷数据、同一种子，按记录的指令重新模拟到第 N tick | 内核不改；代价与 N 成正比 | 从指定局面出发的评测、复现问题局 |
| B 进程分叉 | Linux 上对正在跑的对局进程调 `fork()`，子进程就是一份完整副本 | 内核不改；只能在 Linux 训练机上用 | 训练时从同一局面试多个计划并比较结果 |
| C 真正的存读档 | 给内核全部状态写序列化 | 涉及 144 个源文件，还要新增对拍门禁 | 只有要在玩家设备上做对局内搜索时才值得 |

建议先做 A，它只依赖第 1、2 项基础工作和内核已有的确定性。B 等训练机确定是 Linux 之后再用。C 暂不做。

## 无头批量对局

需要新写两样东西：冷数据缓存，和一个替代 `AISeat` 的纯 C++ 调度循环。吞吐没有实测值，驱动跑通后第一件事就是测它。

### 冷数据缓存

`Session::create` 需要一份 `ColdExport`：冷数据 JSON、图集像素、绘制图集。现在它只能由游戏在开局时现场生成。做法：

1. 给游戏加一个导出开关，开局时把 `ColdExport` 写成文件，每张地图、每种昼夜各一份。
2. 无头驱动读文件，改写种子和双方卡组后调 `Session::create`。卡组在冷数据里是 `players.<席位>.deck` 字符串列表，秘籍在英雄记录里。
3. 用现有的逐 tick 对拍工具验证“改写卡组后载入”与“游戏内用同样卡组开局”一致。这一步不能省，因为有些卡可能还依赖冷数据里的其他字段。

### 调度循环

```
session = Session::create(load_cold(map, decks, seed), map)
while not session.finished() and tick < limit:
    for seat in ai_seats:
        if time >= next_control[seat]:              # 15 Hz
            session.ai_observe(seat)
            if time - plan_at[seat] >= plan_every:
                input = planner_input(seat)
                plan  = planner[seat].plan(input)   # r22 或网络
                recorder.write(tick, seat, input, plan)
            session.ai_control(seat, "r22", send = session.command)
    session.step()                                  # 30 tick/s
recorder.finish(session.result_json())
```

这个循环需要的接口 `Session` 都已经有了。`Session::command` 内部走的是类型化的 `RoomCommands::apply`，不经过 V。要改的只有一处：`ai_plan` 现在把 `AiPlannerR22` 写死在会话里，需要改成可注入的规划器接口（第 5 项基础工作）。

无头驱动不包含选卡阶段。第一版用两种卡组来源：从真实 AI 对局里收集的卡组，和合法范围内的随机卡组。

### 记录格式

每局一个文件，三部分：

| 部分 | 内容 |
| --- | --- |
| 文件头 | `catalog_hash`、`rules_hash`、地图、种子、双方卡组与秘籍、禁卡、`plan_every`、控制频率、双方规划器的名称与版本 |
| 规划记录 | 每次重规划一条：tick、席位、规划器输入的原始事实（英雄、全部单位、卡组冷却、记忆量）、输出的计划字典 |
| 文件尾 | 胜方、结束 tick、双方英雄剩余血量、是否超时 |

落盘的是原始事实而不是编码后的向量。格式先用 JSON Lines，确认字段稳定后再换二进制。

### 并行与评测

- 一局一个进程，几个核就开几个进程。不用线程，避开内核里可能存在的全局状态。
- 评测用固定的（地图，卡组对，种子）列表，新旧规划器跑同一份列表，植物方和僵尸方分开报胜率。
- 胜率接近 50% 时，200 局的 95% 置信区间约为 ±7 个百分点，1000 局约为 ±3 个百分点。判断“新版是否更强”要按这个精度定局数。

## 未确认事项

需要你决定的：

- [ ] 第一版范围是否只做 1v1 对战，2v2 和合作闯关继续用 r22。
- [ ] 训练机是 Windows 还是 Linux。这决定进程分叉方案能不能用，也决定要不要给无头驱动补 Linux 构建。
- [ ] 输出表里各键的上下限。

需要在源码或实测中确认的：

- [ ] 内核单核吞吐，即无头状态下每秒能跑多少 tick。
- [ ] 改写冷数据里的卡组后，对局是否与游戏内同卡组开局逐 tick 一致。
- [ ] 内核里是否有跨对局共享的全局可变状态。这决定同一进程能否连续跑多局。
