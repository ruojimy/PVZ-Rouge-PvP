# 进度（云端第一阶段）

环境：Linux x86-64，g++ 13.3.0，cmake，2 核 Intel Xeon 2.10 GHz，Python 3（只用标准库）。没有 SDL2 开发包，不能装包，不能推送。分支 `ai-nn/foundation`，起点 `1c28636`。

所有命令都在 `dev/` 目录下执行。构建：

```
cmake -S build/ai-nn -B /tmp/ai-nn-build -DCMAKE_BUILD_TYPE=Release
cmake --build /tmp/ai-nn-build -j2
```

下文的"日志摘要"指 `headless_match` 结果行里的 `log_sha256`：对局日志每一条的 JSON 文本，加上每个房间 tick 之后的对局随机数状态摘要，连起来算的 SHA-256。

## 第 1 步 Linux 无头构建与开局加载器

做了什么：

- `build/ai-nn/CMakeLists.txt`：独立的 Linux 构建。内核 144 个源文件、组合层 `match_probe.cpp`、`session.cpp`、`ai_planner_r22.cpp`、`ai/*.cpp`，不含 `cold_export.cpp`、`typed_battle.cpp`、`pvzcore`。编译选项沿用安卓：`-O2 -ffp-contract=off -fno-fast-math`。
- `src/sim/typed72_app/cold_file.{h,cpp}`：从文件（明文或 `.gz`，经系统 zlib）读出 `ColdExport`，并能读数据集的 `index.json`。没有 include `match_probe.cpp`。
- `build/ai-nn/sdl_shim/`：本环境没有 SDL，内核唯一用到 SDL 的 `SDL_SoftStretch` 用自写的同名函数代替（说明见该目录的 `README.md`）。有 SDL2 开发包时 CMake 会自动改用真的。
- `build/ai-nn/src/session_trace.cpp`：对拍用，逐 tick 输出会话路径的随机数摘要、公开快照和日志。

首次完整构建在 2 核上用了 6 分 30 秒。

怎么复跑（第 005 局，先把数据集里的四个文件解压到 `/tmp/c005`，`scenario.json` 内容是 `{"map":"山地","room_ticks":900}`）：

```
cd /tmp/c005
MATCH_SNAPSHOTS=gate_snap.jsonl /tmp/ai-nn-build/typed72_match_gate cold.json atlas.bin scenario.json gate_out.jsonl gate_report.json gate_final.json
/tmp/ai-nn-build/session_trace cold.json atlas.bin atlas.bin.draw.json 900 sess.jsonl 山地
```

b 项的 900 tick 空跑只发生了 3 条日志（两次白天收入），活动很少，所以加了"带 AI 指令的整局"那一项。它的复跑方法：

```
/tmp/ai-nn-build/headless_match --corpus build/ai-nn/cold-corpus --id 005 --out a.jsonl --seq-base 0 --dump-inputs inputs.json --log a.log
cd /tmp/c005 && MATCH_NO_TRACE=1 /tmp/ai-nn-build/typed72_match_gate cold.json atlas.bin inputs.json out.jsonl report.json final.json
# final.json 的 log 数组应与 a.log 逐条相同
```

`--seq-base 0` 是因为门禁程序给场景输入编号从 0 起，而 `AISeat` 从 1 起；序号会写进日志。

遗留问题：

- **与 Windows 的一致性没有验证。** 上面所有比较都是 Linux 上同一份构建的两条路径之间的比较，证明的是"加载器和会话路径没有引入差异"，不是"Linux 结果等于 Windows 结果"。开发机上第 005 局 900 tick 的门禁输出如果能给一份摘要，就能直接比。
- SDL 替身没有和真实 SDL 对比过。它在实测对局里的调用次数见第 2 步。

## 第 2 步 无头对局驱动

做了什么：`build/ai-nn/src/headless_match.cpp`。双方都由 AI 控制，节拍按 `摸底.md` 第 1 节。除了提示词要求的参数，还加了：

- `--id` 可以给逗号分隔的多个局号，在同一进程里连续跑（`--out` 里写 `{id}`）。
- `--dump-inputs` 把 AI 发出的全部指令按房间 tick 导出成门禁程序的场景格式；`--inputs` 读这种文件、不跑 AI、只重放指令。后者就是给开发机对拍用的"外部指令序列"模式。
- `--log` 导出对局日志；`--seat-order`、`--seq-base`、`--no-ai`、`--no-records`、`--digest-every`、`--final-snapshot`。

输出文件不含墙钟时间，同样的参数得到逐字节相同的文件；耗时打印在标准输出。

怎么复跑：

```
/tmp/ai-nn-build/headless_match --corpus build/ai-nn/cold-corpus --id 005 --out /tmp/005.jsonl
python3 build/ai-nn/eval.py --bin /tmp/ai-nn-build/headless_match --corpus build/ai-nn/cold-corpus --out-dir /tmp/eval --ids all --jobs 2
```

### d. 216 局全量

**没有按原计划完成，原因是组合层里有一处只增不减的缓冲，长对局会把内存耗尽。**

发现过程：全量运行中第 050、066、108、114 局的进程涨到 3.3–4.2 GB 后被系统杀掉（`dmesg` 里有 6 条 OOM 记录）。定位：

- 内存随游戏时间增长，所有对局都有，快慢取决于场上的僵尸。第 005 局 252 秒从 197 MB 涨到 272 MB；第 050 局 300 秒涨到 923 MB。
- 只重放指令、不跑 AI 时涨得一样多，门禁程序（`MATCH_NO_TRACE=1`）也一样，所以不在 AI 和会话里。
- `valgrind --tool=massif` 跑第 050 局前 80 秒：增长几乎全部来自 `ContentZombie64Probe::alias_art`（`composition/probes/content_zombies64_probe.cpp` 28 行）里的 `aliases64.push_back(...)`，调用方是 `ContentZombies::art_gate`。同一文件 31 行的 `draws64.push_back(...)` 是同类。
- 这两个数组是探针留证据用的。`match_probe.cpp` 的 `native_tick_done`（1033 行）在 `release_fixtures` 为真时会清空 `units`、`births`、`render_log`、`calls`、`dispatch_calls`、`phase_draws`、`phase_events`，但没有清这两个。`session.cpp` 把 `release_fixtures` 设成了真，所以游戏本体走的也是这条路径。
- 验证：在本地临时给那一行加上 `aliases64=J::array();draws64=J::array();`（**没有提交，补丁里不含**），第 050 局 300 秒的内存稳定在 197 MB 不再增长，日志摘要与未修改时相同（`89af6ffe…`），第 005 局的摘要也相同。速度没有变化。

组合层是生成代码，按提示词的约定我没有改它，只在这里报告。影响：游戏里一局打到二三十分钟、场上长期有走 `art_gate` 的僵尸时，内存会涨到 GB 量级。我没有在游戏本体里验证这一点。

## 第 3 步 卡牌特征表

做了什么：`build/ai-nn/src/card_features.cpp`，导出结果放在 `build/ai-nn/card-features/cards.day.jsonl` 和 `cards.night.jsonl`。

- 第一行是文件头：`catalog_hash`（`438f1abb…`）、`rules_hash`（`ff1bd7ce…`）、字段清单、47 种行为、5 条替换关系。
- 之后每张卡一行（`type: card`），按卡表顺序，内容是 `ColdCatalog::actual(id, 无秘籍, 昼夜)`，也就是对局里实际生效的数值。`catalog_id` 是卡表行自己的 id；派生形态经 `actual` 解析后 `id` 是原卡，`resolved_id` 是形态。
- 再之后是秘籍改写（`type: variant`）：每张非秘籍卡配上同阵营的每一条秘籍，只列出被改动的字段。
- 字段清单取自生成的 `cold_card_fields.h`，卡表以后加字段不用改导出程序。美术、描述和 `native_*` 原始值没有导出。数值字段 30 个（6 个必有、24 个可选），标志位 40 个。

为什么用 `actual` 而不是 `player_card` / `unit_card`：后两个需要具体玩家或具体单位，`actual` 是它们内部做昼夜和秘籍改写的那一层，适合导出静态表。`player_card` 另外做的事只有可用性检查和模仿者的费用。

怎么复跑：`/tmp/ai-nn-build/card_features day out.jsonl`（或 `night`）。

验收结果：

| 验收项 | 结果 |
| --- | --- |
| 行数与卡表一致 | 昼、夜各 232 行，`catalog_id` 232 个互不相同；另有 250 行秘籍改写 |
| 昼夜差异符合 PvP73 规则 | 17 行不同：6 张产出卡（向日葵、双子向日葵、脑光墓碑、水上脑光墓碑、双生脑光墓碑、水上双生脑光墓碑）的 `period` 从 16 变 20；11 张植物蘑菇的 `cost` 加 25。没有其他差异 |
| 重复导出字节相同 | 是 |

遗留问题：秘籍改写只覆盖"单条秘籍"；多条秘籍叠加的效果要在对局里用 `player_card` 现取。

## 第 4 步 规划器接口与记录器

做了什么：

- `ai_planner_r22.h`：新增 `AiPlannerMemory`（r22 的 7 个记忆量）和接口 `IPlanner`（`plan`、`side`、`name`、`memory`、`set_memory`）。`AiPlannerR22` 实现这个接口。
- `session.h` / `session.cpp`：`Session` 新增 `set_ai_planner_factory` 和 `set_ai_plan_observer`；规划器槽位从 `std::optional<AiPlannerR22>` 改成 `std::unique_ptr<IPlanner>`。
- `headless_match` 用 `set_ai_plan_observer` 做记录器：每次重规划写一行 `plan`，含 tick、席位、规划器输入的原始事实（双方英雄、全部单位、卡组）、调用前的记忆、输出的计划，以及网络以后可能要用的上下文（昼夜、是否死斗、卡组冷却、秘籍、计划是否合法）。
- `build/ai-nn/src/replay_planner.cpp`：离线重算。

为什么不改变游戏行为：

1. `AiPlannerR22::plan` 的函数体一个字符都没动，成员变量也没动。新增的 `memory()` 只读，`set_memory()` 游戏里没有调用方。
2. `Session::ai_plan` 里，没有设置工厂时走 `std::make_unique<AiPlannerR22>(side)`，和原来的 `slot.emplace(side)` 构造的是同一个对象；没有设置观察者时不取记忆、不回调。游戏本体不调用这两个新接口。
3. `reset_ai_planner` 仍然是清空槽位。`ai_planner()` 改用 `dynamic_cast`，对 r22 返回的指针和原来一样。
4. `typed_battle.cpp`（V 那一侧的适配层）没有改；用 g++ 对它做语法检查，在新的 `session.h` 下通过。它没有在本环境链接和运行。

## 第 5 步 评测台

做了什么：`build/ai-nn/eval.py`，只用标准库。一局一个进程，按 CPU 核数并行；输出 `summary.json`（确定性，不含墙钟）、`timing.json`（耗时与吞吐）和每局的输出文件。支持按局号、地图名或列表文件选局，`--resume` 续跑，`--memory-limit-mb` 给每个进程设内存上限。

验收结果：

- **没有做"全部 216 局跑两遍"。** 本机 2 核，全量一遍要 90 分钟以上，而且有对局会耗尽内存（第 2 步 d）。实际做的是 35 局的列表（局号 000–017 加家院除 050 外的 17 局）跑两遍，每个进程内存上限 3000 MB。
- 两遍的 `summary.json` 逐字节相同（SHA256 `071323b9…`），其中包含每局输出文件的 SHA256，所以每局的规划记录也逐字节相同。
- 两遍都是 33 局跑完、2 局（048、051）因内存上限以 `std::bad_alloc` 退出。跑完的 33 局：植物胜 16，僵尸胜 17，超时 0。
- 墙钟：第一遍 589 秒，第二遍 639 秒，2 个进程。

遗留问题：全量两遍留给内存问题修复之后，或者核数更多的机器。
