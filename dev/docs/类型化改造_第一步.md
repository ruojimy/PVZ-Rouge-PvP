## 2. 成员类型（34 个场景、每 5 刻采样一次）

| 集合 | 记录数 | 键数 | 类型分布 |
| --- | --- | --- | --- |
| 僵尸 | 64244 | 146 | int 73、bool 25、str 20、float 15、定长数值向量 8（位置 vec4 等）、dict 3 |
| 植物 | 54354 | 88 | int 54、str 13、float 6、bool 5、向量 4、dict 3、list 2 |
| 实体 | 42712 | 61 | str 13、int 13、float 13、bool 11、list 6、向量 3、dict 1 |
| 英雄 | 19965 | 49 | int 29、float 7、bool 6、str 5、vec4 1、list 1 |

结论：85% 以上是标量（数值/布尔/符号），可直接存 double/int/Sym。注意两点：
- **出现与否是语义**（`'灰烬' in z`、`del z[...]`），类型化存储每个字段要带"存在位"；
- **位置等列表是共享引用**（`pos = z['位置']` 后原地改、`current is not original_position`），向量字段要保持引用对象，不能拆成值。

## 3. 访问方式（生成代码统计）

- 原版区段：单位字段大多已走固定成员槽（`rdm/wrm`），开销在 V 数值运算（每个 `+ - * <` 都是一次越界函数调用 + 类型分派）
  和动态函数调用（僵尸区段 157 处 `call(G.出界 / 沉浸播音 / 伤害僵尸 …)`）。
- 补丁模块（bonus_scan、防具显示、弹道几何都在这里）：**每个全局名每次都经 `ns_->get_` 哈希查找**（射击函数里 68 次），
  单位字段用 `__pvz_sb_K_*` 常量作键 → 只能走字典查找，用不上成员槽；函数间调用也全是动态的。
- 闸门链：多层方法闭包 + `callm` 动态派发 + 每次调用打包 Args。

## 4. 第二步计划（按收益/工作量排序）

1. **补丁模块强类型生成**（约 35% 时间所在）：`__pvz_sb_K_*` 等只赋值一次的常量在翻译期折叠成字面键 → 成员槽直访；
   全局名改为缓存的槽指针（保留运行时替换语义）；对未被替换的补丁函数改为直接 C++ 调用。
2. **数值类型推断**：翻译器给局部变量/表达式推断 double（依据 `unit_types.json` 的成员类型 + 字面量 + 算术），
   生成原生 double 运算，只在边界装箱；同时给 V 的数值运算加内联快速路径（覆盖剩余动态代码）。
   先做 `位移处理`、僵尸/植物/实体区段。
3. **闸门链、targets.context、PeriodicTargets 等**手写/类型化，去掉闭包和 Args 打包。
4. **单位强类型存储（T1）**：Obj 槽从 V 改为"标量 + 存在位"，向量/列表/字典字段保持引用；冷路径通过 V 视图按键访问。
   放在 1–3 之后做，因为那时热点代码已不经 V，存储改动的收益才完全释放。

每一步都跑 `tools/check_all.sh`（34 场景逐刻一致）并记录 bench 倍数。

## 第二步 · 第 1 项：补丁模块（11-01 完成）
mixed_late_game：1.82s → **约 1.50s**（`tools/bench.sh` 取 6 次最小值），34 场景逐刻一致。
| 改动 | 效果 |
| --- | --- |
| `fastpath_enabled()` 垫片改为与 Python 默认一致（True）：bonus_scan 对多数僵尸只算上下文净效果 | bonus_scan 21% → 11%，最大一项 |
| `self.__dict__` 实例视图（快速路径的 `_unit_card` 备忘表需要） | 功能补齐 |
| `getattr(x, 名, 默认)` 不再靠抛异常实现（None/数值直接返回默认，实例走不抛异常的查找） | 防具显示包装里每次绘制一次 C++ 异常 → 0 |
| `__pvz_sb_K_*`（377 个只赋值一次的键常量）翻译期折叠为字面键，`x.get("字段")` 对单位直读成员槽 | 约 2% |
| 补丁全局名按编号缓存槽指针（`DynNS::gslot_`，删除时清缓存，保留运行时替换语义） | 同上 |
| `math.*` / `sys._getframe(1)` 经任意别名的模块级导入时内联 | 噪声内 |
| `tools/check_all.sh`：运行前删旧输出，C++ 运行失败时报 FAILED（之前会拿旧文件误报一致） | 对拍可靠性 |

现状按模块自身占比（`PVZ_PROFILE_MODULES=1`）：原版函数 fn_*（主要是 `位移处理`）14.8%、补丁 12.1%（已很分散）、僵尸区段 10.4%、
native_targets 9.2%、native_battle 8.4%、内容 6.7%、扩展 5.6%、周期坐标图 5.5%、物理 4.6%。
下一项：数值类型推断（先 `位移处理` 与三个原版区段），再闸门链/targets 上下文。

## 第二步 · 第 2 项：数值与分派（11-01）
mixed_late_game：1.50s → **1.438s**，34 场景逐刻一致。
| 改动 | 效果 |
| --- | --- |
| V 的 `+ - * / % // 一元- += -= *= <` 与 `==` 加头文件内联的「数值×数值 / 同类型字符串」快速路径（慢路径保留原实现） | 约 2% |
| 生成类的 `slot()/method()/call_method()` 从逐名比较的 if 链（NativeBattle 约 100 个方法、90 个属性，还要逐级落到基类）
  改为整条继承链扁平化的一张表：`SymIndex` 按符号 id 直接下标 + switch（试过 unordered_map，反而慢 15%） | 约 2.5% |
| `getattr(self, "已声明属性", 默认)` 直接读成员槽 | 小 |

结论：原版区段/函数里把数值改成 double 收益有限（`位移处理` 整体只占 6.6%，时间平摊在两次动态调用、地图格子字典查找、
小列表分配上）。剩余开销高度分散（最大的运行时函数 dict_find 10%，调用者分布在十几处），逐点优化每项只有 2–5%。
要再上一个台阶，需要数据结构层面的改造：地图格子改为带固定成员的对象/类型化网格（`ditu[y][x]['方块']` 目前每次字典查找）、
`kong` 等名字集合改为位集、单位存储强类型化、固定函数（出界/不封顶出界）直接调用。
剖析新增：`PVZ_PROFILE_MODULES=1`（按模块自身占比）、`PVZ_PROFILE_FUNCS=<子串>`（按函数）、`PVZ_PROFILE_LINES=<函数>`（按源代码行）。

## 第二步 · 第 3 项：地图格子 / 名字集合（11-01）
1.438s → **1.407s**，34 场景一致。测量后调整了做法：地图格子只有 1–3 个键（方块/里方块/植物），改成 Obj（每个约 6KB、263 个槽）
会让地图占 11MB 且复制变慢；小字典查找本身不慢，慢在 rd→find→dict_find 的越界调用链。改为在 value.h 内联：小字典（<12 键）
字符串键查找、列表/元组范围内下标、列表/集合里查字符串（`in kong`）。

## 现状评估（11-01）
累计 1.82s → 1.407s（约 1.3 倍），相对 Python+_pvpcore（2.33s）约 1.65 倍。剩余时间按调用树：
僵尸闸门链约 10%（十几个内容模块的 zombie_gate/finish_zombie，各 1–9%）、`位移处理` 约 6%、防具显示包装约 5%、
bonus_scan 约 11%（已分散）、周期坐标图约 6%、目标上下文约 9%……没有单个超过 10% 的热点。
逐点优化每项 2–5%；固定函数直接调用估算 2–3%，单位存储改"标量+存在位"估算 3–5%（V 本身已是带标签的标量）。
要到手写 C++ 的 10 倍级，需要的是覆盖整个 PvP 层的"强类型编译"（全程序类型推断：类属性/函数签名/单位记录结构体），
而不是继续逐点。
