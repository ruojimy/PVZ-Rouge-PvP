# 架构与移植路线（2026-11-01 定）

## 为什么用"翻译器 + 动态运行时"
- 原版战斗逻辑只有字节码；PvP 层 Python 约 3.2MB，step 期间实测执行约 1.3 万行（全卡牌/合作/2v2 估计翻倍），
  1.5.0.1 补丁用到 162 个函数约 3500 行。逐行手写既慢又难保证"数值机制全部参照"。
- 方案：`tools/pydec38.py` 反编译原版 → `tools/py2cpp.py` 翻译为 C++（V 动态值运行时）→ 逐刻对拍 Python 参照。
- 性能：单位字典字面量键 = 直接成员槽访问；后续对热点手工特化。

## 运行时分层
- `src/core`：V（Python 值语义）、Obj（单位字典，成员槽 + 附加键）、pyops（运算/内建）、MT19937、Python 数学语义。
- `src/sim/pyrt.h`：Match = 对局命名空间 g（全局名都是 V 成员）；rd/wr/rdm/wrm/call/attr。
- `src/sim/gen/`：翻译生成的原版区段、物理/寻路区段、原版函数（**不手改**，改翻译器或在手写层覆盖）。
- 计划：`src/sim/pvp/` PvP 层（翻译器 v2 类感知版生成初稿 + 手工修正）。

## PvP 层的关键动态机制（翻译时必须保留）
- 区段门控：`_pvp_*` 回调注入到区段字节码（已体现在 extract/live 反编译中）。
- 英雄上下文 NativeTargets.context：把某个戴夫的状态拷入/拷出 g 的"玩家"全局（copy-in/copy-out）。
- HeroProxy：继承 dict、拦截原版代码对 血量/灰烬/冰冻 等的写入 → C++ 单位写入必须经 setm()/setitem() 钩子。
- 原版函数被 PvP 包装覆盖（g["掉血"] 等），所以原版函数一律经 G.名 的函数槽调用。
