# 性能与交互体验优化交接

日期：2026-11-16。目标：在高负载下保持可操作、帧间隔稳定，再争取更高帧率和更接近实时的战斗速度。用户允许尝试更深慢放，并明确由用户负责按键响应和操作手感测试。神经网络 AI 继续暂停。

最新正式交付见第13节及[更新说明](更新说明-PvP74.3-r4.md)。第1–12节保留实施与候选验收历史。

这份交接包含已核实的生产代码、真机数据、独立倍率实验和下一步实施顺序。当前正式版本为 PvP74.3 r4；已验收配置默认启用，完整交付核验见第13节。下文早期建议与r3状态属于历史，不能覆盖最新交付记录。

## 1. 先纠正“最低只能 0.65”

**0.65 是针对固定开销的一层保护，不是硬下限。当前 Application 控制器的目标下限为 0.15；真实模拟过载时已经可以低于 0.65。**

拥有者是 [pressure_pacing.cpp](src/ui/hand/pressure_pacing.cpp)，核心计算为：

```cpp
native_limit = .80 / max(.80, native_cost_ratio);
target = clamp(throughput_estimate, .15, 1.);
target = clamp(max(target, min(.65, native_limit)), .15, 1.);
```

当 native_limit≥0.65 时，最后一行把目标托在 0.65；模拟足够昂贵、native_limit<0.65 时，可以继续下降。源码另有未被真实 App 帧门控接管的旧 AdaptivePacing/RoomWallClock 分支，最低 0.10，不能混作真实 UI 当前策略。

上一轮正式 r3 手机原始 `population_samples` 已观察到：

| 场景 | 采样最低 scale | 最后 scale | 最低 target | 全测量期实际模拟/墙钟 |
| --- | ---: | ---: | ---: | ---: |
| 普通20 | 1.00 | 1.00 | 1.00 | 0.999 |
| 混合120 | 0.65 | 0.65 | 0.65 | 0.664 |
| 高弹幕240 | 0.65 | 0.65 | 0.65 | 0.697 |
| 抓人草120 | 0.45 | 0.45 | 约0.442 | 0.604 |

scale 是当前控制指令，模拟/墙钟是全采样窗口推进率，两者不是同一统计量；暖场后的渐变、积压和恢复都会造成差异。不能因为平均推进率 0.604 就推断最低倍率为 0.604。

现有保护的原意合理：绘制本身慢时，持续降低战斗速度未必能增加 FPS，反而可能把游戏降到接近暂停。但当前成本分组不够准确：`record_advance` 把 Room.update 与 refresh 一起计入推进成本；refresh 中有按发布/刷新次数支付的工作。降低倍率前应分清这些固定成本，否则控制器容易将重复刷新成本误归为每游戏秒模拟成本。

## 2. 已知瓶颈与证据边界

正式 APK 1114083、V2456A / Android 16，固定高HP场景、5秒暖场、原画/像素、自动减绘关闭。完整证据见 [实机评估](test_results/pvp743/device-r3-20261116/assessment.md)。

| 场景 | 呈现 FPS | 呈现间隔 P95 | 每帧模拟 / 刷新 / 绘制均值 |
| --- | ---: | ---: | --- |
| 普通20 | 24.92 | 48.93 ms | 2.47 / 4.54 / 19.41 ms |
| 混合120 | 13.75 | 97.61 ms | 9.20 / 23.69 / 24.43 ms |
| 高弹幕240 | 3.91 | 424.82 ms | 114.23 / 48.91 / 70.34 ms |
| 抓人草120 | 1.55 | 821.43 ms | 468.58 / 66.34 / 79.16 ms |

“刷新”不是屏幕刷新率，而是生产状态向 UI 可读视图的投影/重建等成本。普通场景模拟只占约2.5ms，单靠降倍率很难使它达到60FPS；高负载则同时卡模拟、视图重建和软件绘制。

抓人草独立函数计时约30秒，4809次 NativeTick：

| 互不重叠的阶段 | 总耗时 | 下一步需要细分 |
| --- | ---: | --- |
| plant_actions | 7.41 s | 普通植物、抓人草每头查询、重复周期坐标/索引校验 |
| effects_and_draw_plants | 6.36 s | append_heroes、静态目标注册、hero effects、draw_plants分别计时 |
| setup | 4.88 s | 资源、追踪、区域处理、before_native_tick分别计时 |
| NativeTick整体 | 20.94 s | 上述是其中的子阶段，不能与整体再次相加 |

内嵌热点还有 NativeTracking::begin 728401次/2.65s、head_targets 86638次/1.99s、anchor_head 837373次/0.22s。调用次数高是排查线索，不能只按次数排序：anchor_head次数更多但总耗时小得多。计时本身有开销，最终收益必须回到未启用函数计时的真机测试。

正式 PC↔手机 LAN 输入发送到权威确认 P95=129ms；私有云端高负载自动场景的全会话 P95=1017ms。云端数据含换场边界，且 PC 测试主机限两个逻辑核并通过 WLAN 绑定转发；它能证明当前链路仍有严重延迟，不能单独定位为 relay 问题。手机作为客机时最后抓人草场景约16.85FPS，不执行权威模拟，不能与手机本地1.55FPS直接作优化前后对比。

## 3. 架构判断：值得改调度和数据通路，先分阶段落地

生产 tick 和 command_input 已由 typed C++ Session 执行，诊断中核心 step 的动态 V boxes/calls 为零。当前问题不是再把相同模拟包一层 C++。App编排、完整视图、JSON/V转换、绘制配方重建、重复查询及一次大批模拟仍有高成本。

当前主循环基本是：

```mermaid
flowchart LR
  A[收集输入和网络] --> B[Room.update]
  B --> C[最多12个room step]
  C --> D[完整refresh]
  D --> E[发布快照和音频]
  E --> F[预览与绘制呈现]
  F --> A
```

`Room.update` 一次最多12个room step；常规30Hz room对应每step 8或9个250Hz native tick。因此“12步上限”仍可能一次跑约100个native tick。`typed_battle.cpp` 中这批step连续执行，中间不处理App输入；低倍率只减少应推进量，不给已经开始的长批次抢占能力。

### 阶段 A：输入服务优先的主循环，配合更深慢放

先保留单一权威模拟所有者，将大批推进改为预算内小片段：

1. 每轮先处理输入边沿、松开、网络控制与确认，再推进有限模拟；在安全的完整room/native边界让出。起步实验预算可用4/8ms或1个room step，真实数据决定值，不宣称单个room step一定能低于8ms。
2. 记录“本轮实际完成step数”再从accumulator扣除；保持未完成债务，暂停/后台按已有生命周期契约处理，禁止把慢帧债务截断或重复积分。
3. 如果单个room step已经超过输入预算，需要下一阶段支持可恢复的native阶段状态机；不要在伤害/容器遍历进行一半时随意重入输入处理。
4. 将纯模拟、投影视图、网络冻结/编码、绘制分别计时。先试取消0.65托底，再比较软阈值0.45/0.35/0.20；保持非零下限，0.10只作为极限实验。不要直接把所有对局锁在固定低倍率。
5. 保留开局正常速度、持续压力门控、单次卡顿不触发、恢复迟滞。当前门控用每帧最多0.1秒累积，在1.5FPS下“0.8秒压力”需要约8帧、实际可能超过5秒，应该增加“持续墙钟+多个独立坏帧”的判据测试。
6. 低倍率下长时间无新模拟状态时，UI输入反馈、指针、卡牌选择、摆放预览仍按墙钟更新；世界速度与输入服务频率分开。

新的成本模型建议先采用可解释预算，而不是 `scale=FPS/60`：

```text
U ≈ C_sim × scale + C_view × f_view + C_render × f_render + U_io
scale_target = clamp((U_budget - C_view×f_view - C_render×f_render - U_io) / C_sim,
                     configured_floor, 1)
```

这里 C_sim 为每游戏秒的纯模拟CPU秒，C_view/C_render为每次实际工作成本，频率单位Hz，全部使用互不重复的计时。若固定工作本身已超预算，继续降倍率不会实现目标FPS，必须降低重建频率/画布成本或改变渲染架构。当前手机仅抓人草刷新+绘制均值已约145ms，不能承诺把倍率降到0.2就达到30FPS。

### 阶段 B：让刷新与呈现消费只读帧，减少重复转换

优先实现“权威状态版本→只读轻量呈现帧”，再考虑拆线程。一个版本只提取一次，按消费者复用，不要每个输入、每个显示帧、每个网络玩家重新构造同一大对象。

- 把本机呈现所需的位置、姿态、资源、冷却、可部署性，与完整回放/网络快照分开。无模拟变化也无规则变化时，复用之前的世界帧；仍刷新本机鼠标/触控预览。
- typed Session到本机渲染优先传紧凑C++结构/不可变句柄，减少`typed→JSON→V→绘制配方`往返。已有native_frame与frame cache应复用，先量化实际重复转换，不重复造同功能模块。
- 同一主线程先分开服务/模拟/发布/显示节奏。若仍无法满足输入服务预算，再试模拟独立worker、UI/SDL留在主线程；worker独占可变战斗状态，经有界SPSC命令队列与最新不可变帧交换。禁止共享V对象跨线程或持有全局锁等待慢渲染。
- world帧可只保留最新已完成版本；部署结果、资源扣除、跳跃边沿、终局等可靠事件不能被“只保留最新”吞掉。帧池必须有明确容量、消费者生命周期及退出清理。

### 阶段 C：降低热点工作量，而不仅是函数调用语法开销

- `NativeTracking::prepare_chart` 即使缓存命中仍逐项核对实时坐标。评估统一版本/dirty标记与分阶段重建，但必须覆盖所有移动、变形、Motion指针替换、英雄代理切换和周期坐标移动；未覆盖写入点前不能删实时校验。
- 抓人草多个头查询可共享同一阶段的候选集或索引，分别保留每头精判、优先级和攻击时机。精确伤害/触手生长/不同体积/跨环边界必须对拍。
- 每tick重建的桶、临时vector、完整目标范围检查，按profile决定复用容量和脏区更新。缓存键包括地图/地形/队伍/状态版本，不用“看起来没变”作假设。
- AI、低频经济、静态地形、纯装饰可以研究不同更新频率；碰撞、命中和已有250Hz逻辑不能直接降成30/60Hz。若要改变规则节拍，另列版本兼容、回放及机制迁移项目。
- `session.cpp` 明确提示draw hooks携带状态。删除未呈现的draw之前，先拆开副作用和纯绘制；不能把全部中间draw无条件跳过。

### 阶段 D：渲染提速

当前 `src/pg/system.cpp` 最终把软件画布通过 `SDL_UpdateTexture` 上传后呈现；用了SDL GPU呈现不代表各单位绘制已GPU批处理。

先做画布尺寸/分层缓存/透明区域裁剪/配方缓存命中率/脏区的量化；再给高频精灵建立图集、持久纹理和批量变换绘制原型。复杂像素操作保留软件回退。用户材质只影响显示，不写生产模拟图集或粒子采样。

目标是轻场景60FPS、重场景先稳定30FPS，作为待验证工程目标而非承诺。帧间隔P95/P99和长帧数量比短时平均FPS更重要。低画质只能调整世界层，文字、按钮和摆放网格保持可读；不能靠模糊整屏隐藏性能缺口。

## 4. 交互与联机的硬约束

用户负责按键和手感验收；开发者负责记录各阶段时间与队列。至少区分：设备事件采集→排队→权威接收→在指定tick应用→结果快照→呈现函数返回。发送到ACK不是物理触控到光子的延迟。

| 输入 | 可以优化 | 必须保留 |
| --- | --- | --- |
| 移动按住/松开 | 合并过期的连续状态，立即记录最新方向 | 松开不可丢；场景切换/后台清输入；不能把跳跃边沿一起覆盖 |
| 连跳/短按 | 单独有序边沿队列，尽快在合法tick处理 | 同帧多次边沿及0.40游戏秒跳跃窗口，不因渲染丢键 |
| 种植/墓碑/放置/取消 | 立即本地按下反馈和预览，独立可靠请求/结果通道 | 请求ID、去重、顺序、合法性、资源扣除、明确失败；预览不冒充成功 |
| 选择卡牌/菜单/拖拽 | 按墙钟高频服务，本机UI可先响应 | 不受慢放倍率缩慢，不让整世界刷新阻塞简单选择反馈 |

接受请求和战斗实际应用是两种确认，界面与日志不能混淆。低倍率会让世界移动和跳跃过程变慢，这是全局慢放；不要擅自只把玩家英雄提回1x，否则会改变碰撞、伤害、公平性及回放。若之后尝试本地英雄预测，只用于显示并由权威纠正；传送、死亡、跳跃校验、放置结果不能无限外推。

网络继续沿用r3已实现的后台打包、每玩家快照替换队列和有界缓冲。下一步把低频大世界快照与高频小型输入确认/英雄状态分开，减少可靠大帧的队头阻塞。先在现有协议中做独立消息和版本协商原型；是否需要独立连接或UDP/QUIC等传输另以丢包、乱序、跨平台和部署成本验证，不能直接替换生产链路。

慢客机只对自己的快照降频；控制消息不随世界慢放；主机统一权威倍率。观众不能把正常玩家一起拖慢。减绘和插值已有实现（正常最多约50ms、慢放最多约120ms位置平滑），不要再靠增加数百毫秒插值来掩盖排队。

## 6. 验证与发布要求

1. 自动场景：普通20、混合120、高弹幕240、抓人草120；追加独立芦笋战机。对照保持同设备、画布/特效、HP、暖场、输入、逻辑tick或明确墙钟分母。自适应稳态另给至少30–60秒窗口；短tick实验不能代替长时稳态。
2. 拆两类对照：固定逻辑tick验证同样战斗工作和状态/RNG；固定墙钟验证实际FPS、倍率、积压和体验。降倍率导致少模拟了内容，不能包装为等量工作加速。
3. 指标：显示/服务帧间隔P50/P95/P99、>100/250ms长帧、纯模拟每tick成本、投影/编码次数、快照年龄、输入各阶段延迟、scale轨迹、实际推进率、CPU/内存/温度。函数计时默认关，单独记录诊断开销。
4. 用户人工：移动立即起步和松开停止、两次短跳/连跳、选卡拖动、合法/非法种植、墓碑与放置、取消、镜头/触控、后台恢复。分别记录普通/重载、倍率、主客角色及用户结论；未反馈不记通过。
5. 初步工程门槛建议：本地UI反馈P95≤50ms、服务间隔P95≤16.7ms/P99≤33ms；权威输入到应用P95≤100ms；LAN ACK P95≤150ms；正常公网目标≤250ms并扣清基础RTT。它们是讨论起点，达不到就如实报告，不为达标改计时起止点。
6. 保持250Hz规则语义、伤害、RNG消费顺序、回放哈希、全席位输入顺序。开启/关闭候选开关逐项对拍，包含同frame多次输入、tick边界部署、周期地图、变形/死亡/复活和后台。
7. 旧全量2366项为2324 PASS/30 FAIL/12 ERROR，15精确豁免、27未豁免，仍非全产品通过。候选定向通过不替代该门禁；发布按改动范围补足必要回归与实机。
8. 生产内核和组合源位置遵守AGENTS.md；只读`next-pvp71`不得改。UI重生成后运行材质/741 hooks及网络拥有层检查。最终EXE/APK/源码归档、根启动器SHA、最近一组备份和独立存档保护一起交付。

## 7. 本轮隔离倍率实验及人工入口

工具：`src/uitools/pvp743_pacing_lab.cpp`、`tools/pvp743_pacing_lab.py`。它使用现有生产库和真实Application循环，在测试回调中覆盖下一轮使用的倍率；不是正式自适应控制器补丁。没有修改已发布r3 EXE/APK。

非交互模式按同seed和高HP抓人草120，暖场150 room tick、测量150 room tick，最终300 room tick；每个测量期1250 native tick。依次比较auto、0.65、0.35、0.20。限制两个逻辑核、BelowNormal、单进程串行；SDL dummy完成的软件绘制循环，不代表物理屏幕FPS或Android收益。

运行：

```powershell
python -X utf8 tools/pvp743_pacing_lab.py --out test_results/pvp743/pacing-new-run
```

人工体验由用户控制按键，单组独立窗口示例：

```powershell
python -X utf8 tools/pvp743_pacing_lab.py --interactive --scales 0.35 --seconds 180 --out test_results/pvp743/pacing-manual-035
```

输出目录必须不存在；可把0.35换成auto、0.65、0.20。该入口开启正常输入，使用独立测试userdata并自动布景，180秒后导出；提前退出会保留日志并报告未完成。资源和冷却仍按对局规则约束，操作失败要先区分资源/冷却/位置与响应延迟；正式人工部署验收应另准备足额资源的专用场景。可视交互分支尚未由用户验收，不能标手感通过。

结论：在这一小段相同战斗工作中，更深慢放确实能腾出更多显示机会，值得做正式控制策略候选。**平均31.94仍伴随P95约87ms，所以不能称稳定30FPS或操作舒适。** 每个逻辑step较重时会形成“几帧轻、随后一帧重”的节奏，下一步仍需缩短模拟批次、减少刷新/绘制工作并由用户判断手感。

在相同1250 native tick内，模拟总耗时约3.0–3.5秒，而刷新累计从约1.80秒增长到8.83秒、绘制从约1.03秒增长到9.91秒；更多显示机会也带来更多固定工作。这进一步支持按版本复用视图和分离呈现数据的优先级。最终状态一致只覆盖本次固定中性输入场景，不覆盖真人输入/联机/所有机制。

人工命令目前只用于PC实验窗口。正式r3手机诊断Intent尚未暴露`fixed_scale`，下一轮应为诊断APK增加显式受限参数并核对实装版本；不能向旧APK传一个未知字段就声称手机倍率已改变。用户尚未验收本轮实验的按键响应，文档中该项保持待测。
